Java Basics — Production Engineering Perspective

JVM internals, compilation flow, memory architecture, primitives — why these matter at runtime

1. JDK vs JRE vs JVM — The Actual Difference

JDK (Java Development Kit) — what YOU install to write Java javac (compiler), java (launcher), javap (bytecode inspector), jstack (thread dump), jmap (heap dump), jconsole (JVM monitoring), jar, keytool, plus the JRE JRE (Java Runtime Environment) — what end-users need to RUN Java JVM + standard library classes (java.lang, java.util, java.io, ...) → Spring Boot fat JAR bundles the JRE logic, not this directly JVM (Java Virtual Machine) — the actual execution engine Interprets/compiles bytecode to native machine code Manages memory (heap, stack, metaspace) Performs garbage collection Every JVM implementation (HotSpot, GraalVM, OpenJ9) differs in tuning Production truth: Docker container ships your JAR + JRE (eclipse-temurin:21-jre ~220MB) GraalVM Native Image: compiles to native binary — no JVM at runtime! Spring Boot 3 + GraalVM: startup 3s → 50ms, memory 300MB → 50MB

2. Compilation Flow — Source to Execution

Step 1: Compilation (javac) OrderService.java │ lexical analysis → tokens │ syntax analysis → AST (Abstract Syntax Tree) │ semantic analysis → type checking, name resolution │ bytecode generation ▼ OrderService.class ← platform-independent bytecode (binary: 0xCAFEBABE magic header + bytecode instructions) Step 2: Class Loading (JVM startup) Bootstrap ClassLoader → loads java.*, sun.* from rt.jar/modules Platform ClassLoader → loads javax.*, jdk.* extensions Application ClassLoader→ loads YOUR classes from classpath Spring's LaunchedURLClassLoader → loads from nested JAR files Step 3: Bytecode Interpretation → JIT Compilation JVM interprets bytecode (slow, ~1000 invocations) C1 Compiler: quick compilation, basic optimizations C2 Compiler: aggressive optimization after ~10,000 invocations → Method inlining, escape analysis, loop unrolling Result: native machine code, cached in Code Cache (off-heap!)

3. JVM Memory Architecture — Production Impact

Heap (GC-managed, -Xms/-Xmx) Young Generation: Eden Space ← new objects allocated here Survivor S0/S1 ← objects that survived Minor GC Old Generation ← long-lived objects (Spring beans, caches, connection pools) Stack (per-thread, -Xss) Each thread: its own stack Contains: method frames (local vars, operand stack, return address) 200 Tomcat threads × 512KB = ~100MB just for stacks! StackOverflowError: too many nested frames (recursive calls) Metaspace (native memory, -XX:MaxMetaspaceSize) Class metadata: field names, method signatures, bytecode Static variables (references stored in heap objects) Interned strings (Java 8+: in heap) Risk: ClassLoader leak → metaspace fills → OutOfMemoryError: Metaspace Code Cache (JIT-compiled code, off-heap) If full: JVM deoptimizes → performance cliff! -XX:ReservedCodeCacheSize=256m (default often 48m — too small for Spring Boot)

4. Primitive Types vs Reference Types

// Primitives: stored directly on stack (if local variable)
// or embedded in object (if field)
int    count = 42;       // 4 bytes, stack local variable
long   id = 100L;       // 8 bytes
double price = 9.99;    // 8 bytes, IEEE 754
boolean flag = true;    // JVM uses int internally (1 bit concept, 4 bytes reality)
char   c = 'A';         // 2 bytes, UTF-16

// Reference types: variable holds address, object is in heap
String name = "Alice";  // name (4 bytes ptr on stack) → heap object
List<Order> orders = new ArrayList<>();  // ptr → ArrayList object → heap

// CRITICAL: Integer cache (-128 to 127 cached)
Integer a = 127;
Integer b = 127;
System.out.println(a == b);    // true! (same cached object)
Integer x = 128;
Integer y = 128;
System.out.println(x == y);    // FALSE! (different heap objects)
System.out.println(x.equals(y)); // true (value comparison)
// Rule: ALWAYS use .equals() for object comparison, NEVER == for Integer, String

// String Pool — interview trap
String s1 = "hello";         // from string pool
String s2 = "hello";         // same pool object
String s3 = new String("hello"); // new heap object!
System.out.println(s1 == s2);  // true (same pool object)
System.out.println(s1 == s3);  // FALSE (different objects)
// String.intern() → adds to pool, returns pool reference

5. Autoboxing Overhead — Performance Trap

// Autoboxing: primitive → wrapper object (auto)
// Unboxing: wrapper object → primitive (auto)
List<Integer> list = new ArrayList<>();
for (int i = 0; i < 1_000_000; i++) {
    list.add(i);  // AUTOBOXING: creates 1M Integer objects on heap!
    // Each Integer: 16 bytes object header + 4 bytes value = 20 bytes
    // vs int[]: 4 bytes each → 5× memory waste
}

// PRODUCTION FIX: use primitive arrays or specialized libraries
int[] primitiveArray = new int[1_000_000]; // ~4MB vs ~20MB

// Common autoboxing bug:
Long sum = 0L;
for (long i = 0; i < 1000; i++) {
    sum += i;  // sum unboxed → long add → reboxed → 1000 Long objects created!
}
// Fix: use long sum = 0L; (primitive)

// NullPointerException from unboxing
Integer value = null;  // from database/map lookup
int x = value;         // NPE! unboxing null throws NullPointerException

Object-Oriented Programming in Java

Encapsulation, inheritance pitfalls, SOLID, composition vs inheritance — production engineering lens

1. Encapsulation — More Than Getters/Setters

// Weak encapsulation: exposes internals
public class Order {
    public List<OrderItem> items = new ArrayList<>(); // ❌ internal exposed
    public double totalAmount;                         // ❌ can be set inconsistently
}
// Caller: order.items.add(item); order.totalAmount += item.price;
// Now business logic is scattered everywhere → bugs, inconsistency

// Strong encapsulation: invariants enforced by the class itself
public class Order {
    private final List<OrderItem> items = new ArrayList<>();
    private BigDecimal totalAmount = BigDecimal.ZERO;
    private OrderStatus status = OrderStatus.PENDING;

    public void addItem(OrderItem item) {
        if (status != OrderStatus.PENDING)
            throw new IllegalStateException("Cannot modify confirmed order");
        items.add(item);
        totalAmount = totalAmount.add(item.getTotalPrice()); // always consistent
    }

    // Return defensive copy — never expose mutable internal state
    public List<OrderItem> getItems() {
        return Collections.unmodifiableList(items); // ❌ can't modify external
    }
}

2. Inheritance — When It Becomes Dangerous

// Inheritance danger: Fragile Base Class Problem
class HashSet<E> {
    private int addCount = 0;

    public boolean add(E e) {
        addCount++;
        return super.add(e);  // addAll() internally calls add() too!
    }

    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();  // WRONG: add() called for each element
        return super.addAll(c); // → add() increments again → double count!
    }
}
// Classic Java design mistake (documented in Effective Java Item 18)

// Liskov Substitution Principle violation:
class Rectangle {
    protected int width, height;
    public void setWidth(int w) { width = w; }
    public void setHeight(int h) { height = h; }
}
class Square extends Rectangle {
    public void setWidth(int w) { width = height = w; }   // breaks Rectangle contract!
    public void setHeight(int h) { width = height = h; }
}
// Code using Rectangle: rect.setWidth(4); rect.setHeight(5); area() expects 20
// With Square: area() = 25 (height also set to 5) → LSP violated!

// ❌ Deep inheritance → brittle, hard to test, Spring proxying issues

// If code expects a List, it should work with ReadOnlyList for read operations
// BUT: if code calls add(), it will throw — LSP violation!

    // OrderService doesn't know or care about implementation
}

Java Collections Framework — Internals

HashMap internals, collision resolution, time complexity, concurrent collections, production tradeoffs

1. HashMap Internal Architecture

HashMap = array of buckets + linked list/tree per bucket Internal array: Node<K,V>[] table (default capacity 16) put("Alice", user): 1. hash("Alice") → hashCode() + secondary mixing 2. index = (capacity - 1) & hash → bucket index (e.g., 7) 3. table[7] is empty → create Node, store there put("Bob", user): 1. hash("Bob") → different hash, maps to index 11 2. table[11] empty → store Collision: put("Carol", user) maps to index 7 (same as Alice): 3. table[7] has Alice → traverse linked list 4. .equals("Carol") != "Alice" → append Node at end Java 8+: if bucket has ≥8 entries → convert to Red-Black Tree (O(log n))! Load Factor (default 0.75): When size > capacity × 0.75 → RESIZE (double capacity, rehash all entries!) 16 entries → resize at 12 → new capacity 32 32 entries → resize at 24 → new capacity 64 Rehashing: expensive! O(n) — all entries rehashed Fix: pre-size HashMap: new HashMap<>(expectedSize / 0.75 + 1)

3. Fail-Fast vs Fail-Safe Iterators

// Fail-fast: throws ConcurrentModificationException if modified during iteration
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if (s.equals("b")) list.remove(s);  // ConcurrentModificationException!
}
// Happens because: modCount changes → iterator.next() detects mismatch

// ✅ Fix 1: use removeIf (safe)
list.removeIf(s -> s.equals("b"));

// ✅ Fix 2: collect and remove
List<String> toRemove = list.stream().filter(s -> s.equals("b")).toList();
list.removeAll(toRemove);

// ✅ Fix 3: iterator.remove()
Iterator<String> it = list.iterator();
while (it.hasNext()) { if (it.next().equals("b")) it.remove(); }

// Fail-safe: CopyOnWriteArrayList (for reads >> writes)
// Works on copy → no ConcurrentModificationException
// But: add() copies entire array → O(n) → expensive for frequent writes
// Use for: Spring event listeners, rarely-changing config lists
List<String> safeList = new CopyOnWriteArrayList<>();
for (String s : safeList) { safeList.add("x"); } // no exception (reads snapshot)

4. ConcurrentHashMap vs synchronizedMap

// ❌ Hashtable/Collections.synchronizedMap: locks ENTIRE map per operation
Map<String, Integer> map = Collections.synchronizedMap(new HashMap<>());
// get() locks whole map → no concurrent reads → bottleneck at scale

// ✅ ConcurrentHashMap: locks only the BUCKET (segment)
Map<String, Integer> cmap = new ConcurrentHashMap<>();
// Java 8+: uses CAS + synchronized on Node (bucket level)
// Multiple reads: fully concurrent (no locks)
// Writes to different buckets: concurrent
// Writes to same bucket: synchronized on that bucket only

// Atomic compound operations:
cmap.putIfAbsent("key", 0);         // atomic: add only if absent
cmap.computeIfAbsent("key", k -> computeExpensive(k)); // atomic compute
cmap.merge("count", 1, Integer::sum); // atomic increment counter!

// ❌ Common mistake: non-atomic compound operation
if (!cmap.containsKey("k")) cmap.put("k", value); // NOT atomic! Race condition!
// ✅ Use putIfAbsent() instead

// Comparable: natural ordering (class defines its own)
public class Product implements Comparable<Product> {

Collections.sort(products);  // uses compareTo

Java Exception Handling

Hierarchy, checked vs unchecked, Spring Boot global handling, anti-patterns, production practices

1. Exception Hierarchy

Throwable ├── Error (JVM-level, don't catch) │ ├── OutOfMemoryError │ ├── StackOverflowError │ └── VirtualMachineError │ └── Exception ├── Checked Exceptions (must declare or catch) │ ├── IOException │ ├── SQLException │ ├── ClassNotFoundException │ └── your custom checked exceptions │ └── RuntimeException (unchecked, no forced handling) ├── NullPointerException ├── IllegalArgumentException ├── IllegalStateException ├── IndexOutOfBoundsException ├── ClassCastException └── your custom unchecked exceptions Production rule: In modern Java/Spring, use UNCHECKED exceptions almost exclusively. Checked exceptions leak implementation details, pollute method signatures, force callers to handle or rethrow, and become unmanageable in lambdas.

3. Global Exception Handler — Spring Boot

@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handleNotFound(ResourceNotFoundException ex) {
        log.warn("Resource not found: {}", ex.getMessage());  // WARN not ERROR (expected)
        return ErrorResponse.of(ex.getErrorCode(), ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors()
            .stream().collect(Collectors.toMap(
                FieldError::getField, FieldError::getDefaultMessage,
                (existing, replacement) -> existing  // on duplicate key
            ));
        return ErrorResponse.validation(errors);
    }

    @ExceptionHandler(ApplicationException.class)
    public ResponseEntity<ErrorResponse> handleAppException(ApplicationException ex) {
        log.warn("Application exception [{}]: {}", ex.getErrorCode(), ex.getMessage());
        return ResponseEntity.status(ex.getHttpStatus())
            .body(ErrorResponse.of(ex.getErrorCode(), ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ErrorResponse handleGeneral(Exception ex, HttpServletRequest request) {
        String traceId = MDC.get("traceId");
        log.error("Unexpected error [traceId={}] at {}: {}",
            traceId, request.getRequestURI(), ex.getMessage(), ex);
        // NEVER expose: stack trace, internal messages, class names to client!
        return ErrorResponse.of("INTERNAL_ERROR",
            "An error occurred. Reference: " + traceId);
    }
}

4. Anti-Patterns to Avoid

❌ Exception Anti-Patterns
// 1. Swallowing exceptions
try {
    process();
} catch (Exception e) {
    // silent — debugging nightmare!
}

// 2. Using exceptions for flow control
try {
    return map.get(key);
} catch (NullPointerException e) {
    return defaultValue;  // use getOrDefault()!
}

// 3. Catching too broadly
catch (Exception e) { log.error(e.getMessage()); }
// Catches OutOfMemoryError too! Use Throwable carefully.

// 4. Re-wrapping losing stack trace
catch (IOException e) {
    throw new AppException("IO error");  // loses cause!
}
✅ Good Practices
// 1. Log OR throw, not both
catch (Exception e) {
    log.error("Failed to process", e); // then don't rethrow
    // OR: throw, let global handler log
}

// 2. Preserve stack trace
catch (IOException e) {
    throw new AppException("IO error", e); // pass cause!
}

// 3. Try-with-resources (always!)
try (InputStream is = openStream()) {
    process(is);
} // auto-closes even on exception

// 4. Specific exception types
catch (HttpClientErrorException e) { ... }
catch (HttpServerErrorException e) { ... }

Java I/O & NIO

Blocking vs non-blocking, channels, buffers, scalability, file handling, socket communication

1. Traditional I/O — Thread-Per-Connection Problem

Blocking I/O model (java.io): Client-1 connects → Thread-1 assigned (blocks on read()) Client-2 connects → Thread-2 assigned (blocks on read()) Client-N connects → Thread-N assigned (blocks on read()) 10,000 clients = 10,000 blocked threads Each thread: ~512KB stack = 5GB just for stacks! CPU: context switching overhead between 10K threads → System collapses under load Why Tomcat default is 200 threads: This is the maximum concurrent blocking I/O operations At 200ms avg request: 200 threads ÷ 0.2s = 1000 req/s max Beyond 200 concurrent: requests queue → timeouts → 503s

2. Java NIO — Non-Blocking I/O

// NIO: Buffer-oriented, channel-based, non-blocking
// Key concepts:
// Channel: bidirectional data pipe (SocketChannel, FileChannel)
// Buffer: holds data being read/written (ByteBuffer, CharBuffer)
// Selector: monitors multiple channels for events

// Buffer usage (MUST know flip() / clear() / rewind())
ByteBuffer buffer = ByteBuffer.allocate(1024);    // heap buffer
ByteBuffer direct = ByteBuffer.allocateDirect(1024); // off-heap, faster for IO

// Writing to buffer:
buffer.put("Hello".getBytes());                  // position moves
buffer.flip();                                      // position=0, limit=written bytes

// Reading from buffer:
while (buffer.hasRemaining()) {
    byte b = buffer.get();                         // reads one byte
}
buffer.clear();                                     // reset for reuse

// Non-blocking server with Selector (simplified):
Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.configureBlocking(false);                  // non-blocking!
server.bind(new InetSocketAddress(8080));
server.register(selector, SelectionKey.OP_ACCEPT); // register interest

while (true) {
    selector.select();                              // blocks until event
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isAcceptable()) {
            SocketChannel client = server.accept();
            client.configureBlocking(false);
            client.register(selector, SelectionKey.OP_READ);
        }
        if (key.isReadable()) { handleRead(key); }
    }
}
// ONE thread handles thousands of connections! → Netty, Spring WebFlux use this pattern

3. Files API — Production File Handling

// Modern: java.nio.file.Files (Java 7+) — preferred over File class
Path path = Path.of("/data/uploads/file.csv");

// Reading (choose based on file size):
String content = Files.readString(path);                       // whole file into String
List<String> lines = Files.readAllLines(path);                  // all lines into List (⚠️ memory!)
try (Stream<String> stream = Files.lines(path)) {              // ✅ streaming (memory-efficient)
    stream.filter(line -> !line.startsWith("#")).forEach(processor::process);
}

// Writing:
Files.writeString(path, content, StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING);
Files.write(path, lines, StandardCharsets.UTF_8);

// Copy/Move/Delete:
Files.copy(source, target, StandardCopyOption.REPLACE_EXISTING);
Files.move(source, target, StandardCopyOption.ATOMIC_MOVE);  // atomic on same filesystem
Files.deleteIfExists(path);

// File upload in Spring Boot:
@PostMapping("/upload")
public String upload(@RequestParam MultipartFile file) throws IOException {
    Path destination = Path.of(uploadDir, UUID.randomUUID() + "_" + file.getOriginalFilename());
    Files.createDirectories(destination.getParent());
    try (InputStream input = file.getInputStream()) {
        Files.copy(input, destination, StandardCopyOption.REPLACE_EXISTING);
    }
    return destination.getFileName().toString();
}

Java Generics — Deep Understanding

Type erasure, wildcards, covariance, bounded types, Spring/Hibernate usage, runtime limitations

1. Why Generics Exist — Type Safety Before Runtime

// Without generics (Java 1.4): runtime ClassCastException
List list = new ArrayList();
list.add("hello");
list.add(42);         // compiles! Different types mixed
String s = (String) list.get(1);  // ClassCastException at runtime!

// With generics: compile-time safety
List<String> strings = new ArrayList<>();
strings.add("hello");
strings.add(42);    // COMPILE ERROR — caught before deployment!
// No cast needed: String s = strings.get(0);

2. Type Erasure — The Runtime Reality

Generics exist ONLY at compile time. At runtime: erased to raw types. List<String> → List (with checkcast bytecode at use sites) List<Integer> → List At runtime: List<String> and List<Integer> are THE SAME type! Runtime limitation: new T() → IMPOSSIBLE (can't instantiate type param at runtime) new T[10] → IMPOSSIBLE (generics + arrays = trouble) obj instanceof List<String> → COMPILE ERROR (can't check generic type at runtime) obj instanceof List<?> → OK (raw type check) list.getClass() == List.class → always true regardless of T Bridge methods: class Foo implements Comparable<Foo> { int compareTo(Foo o) } Erasure: Comparable needs compareTo(Object o) → compiler generates BRIDGE method: synthetic compareTo(Object o) { return compareTo((Foo) o); } This makes polymorphism work with erasure!

3. Wildcards — PECS Rule

// Producer Extends, Consumer Super (PECS) — Joshua Bloch's rule

// ? extends T: Producer — you can READ T from it, not write
public void processOrders(List<? extends Order> orders) {
    for (Order o : orders) { process(o); }  // ✅ read as Order
    // orders.add(new Order()); ← COMPILE ERROR (can't write!)
    // Why? List could be List<PremiumOrder> — adding base Order would be wrong
}
processOrders(premiumOrders);   // List<PremiumOrder> works!
processOrders(regularOrders);   // List<RegularOrder> works!

// ? super T: Consumer — you can WRITE T to it, reading is Object
public void addOrders(List<? super Order> destination) {
    destination.add(new Order());       // ✅ write Order is safe
    destination.add(new PremiumOrder()); // ✅ PremiumOrder IS-A Order
    // Order o = destination.get(0); ← must use Object
}

// Classic example: Collections.copy()
public static <T> void copy(List<? super T> dest, List<? extends T> src) { ... }
// dest is consumer (? super T), src is producer (? extends T)

3. Stream Performance Pitfalls

❌ Stream Performance Anti-Patterns
// 1. Stream for simple iteration
list.stream().forEach(System.out::println);
// vs: list.forEach(System.out::println); (faster, no stream overhead)

// 2. sorted() on large streams
orders.stream()
    .sorted()              // buffers ALL to sort — O(n log n) + O(n) memory
    .limit(10).toList();   // better: sort + limit at DB level

// 3. Parallel stream for small collections
list.parallelStream()      // fork-join overhead > benefit for <10K elements
    .map(expensive).toList();

// 4. Boxing/unboxing in numeric streams
orders.stream()
    .map(Order::getAmount)       // Stream<BigDecimal>
    .mapToLong(BigDecimal::longValue) // but what about primitives?
✅ Efficient Streams
// Use IntStream/LongStream for primitives
long sum = IntStream.rangeClosed(1, 1000000)
    .asLongStream()
    .sum();  // no boxing!

// Parallel only for CPU-bound, large data
orders.parallelStream()          // 100K+ elements
    .filter(o -> isExpensive(o)) // CPU-bound check
    .toList();

// Terminate early when possible
boolean anyPending = orders.stream()
    .anyMatch(o -> o.getStatus() == PENDING);
// Stops at first PENDING — doesn't scan all

Java Concurrency — OS & Backend Perspective

Thread lifecycle, locks, atomics, CompletableFuture, memory model, production patterns

1. Thread Lifecycle & JVM Scheduling

Thread states (OS maps to: Running / Runnable / Blocked): NEW → created, not started RUNNABLE → started, may be on CPU or waiting for CPU time slice BLOCKED → waiting for monitor lock (synchronized block) WAITING → Object.wait(), Thread.join(), LockSupport.park() TIMED_WAIT → Thread.sleep(n), Object.wait(n) TERMINATED → run() completed or exception thrown Context switch cost: Save current thread's CPU registers + program counter (~100 nanoseconds) Load next thread's saved state Cache effects: new thread's data not in L1/L2 cache → cache misses Full context switch: ~1-10 microseconds JVM threads map 1:1 to OS threads (platform threads) Java 21 Virtual Threads: JVM-managed, mount/unmount on carrier OS threads Blocking IO: virtual thread unmounts → carrier thread free → 0 waste

2. Synchronized vs ReentrantLock

// synchronized: JVM built-in, simple but limited
public synchronized void withdraw(double amount) {
    // intrinsic lock on 'this' — one thread at a time
    // Cannot: timeout, interruptible, try-lock, read/write lock
    balance -= amount;
}

// ReentrantLock: explicit, more control
private final ReentrantLock lock = new ReentrantLock(true); // fair=true: FIFO ordering

public void transfer(double amount) throws InterruptedException {
    if (lock.tryLock(5, TimeUnit.SECONDS)) {  // timeout! doesn't block forever
        try {
            balance -= amount;
        } finally {
            lock.unlock();   // MUST unlock in finally!
        }
    } else {
        throw new IllegalStateException("Could not acquire lock");
    }
}

// ReadWriteLock: multiple readers OR one writer
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();

public Object get(String key) {
    rwLock.readLock().lock();    // multiple threads can hold readLock simultaneously
    try { return cache.get(key); } finally { rwLock.readLock().unlock(); }
}

public void put(String key, Object value) {
    rwLock.writeLock().lock();   // exclusive! no readers while writing
    try { cache.put(key, value); } finally { rwLock.writeLock().unlock(); }
}

3. Java Memory Model — visibility

// Without volatile: compiler/CPU may cache in register → other threads don't see update!
class BrokenStopFlag {
    private boolean running = true;  // not volatile!

    public void stop() { running = false; }
    public void run() {
        while (running) { work(); }  // might never see running=false! Infinite loop!
    }
}

// volatile: guarantees visibility (not atomicity!)
private volatile boolean running = true;  // reads always from main memory

// AtomicInteger: visibility + atomicity via CAS (Compare-And-Swap)
private final AtomicInteger counter = new AtomicInteger(0);
int newVal = counter.incrementAndGet();     // atomic: read-increment-write
counter.compareAndSet(5, 10);             // atomic: if value==5, set to 10

// ConcurrentHashMap.compute() for atomic map operations:
ConcurrentHashMap<String, AtomicInteger> counts = new ConcurrentHashMap<>();
counts.computeIfAbsent("key", k -> new AtomicInteger(0)).incrementAndGet();

Java Memory Management

GC algorithms, generations, reference types, memory leaks, OOM scenarios, monitoring

1. Garbage Collection — Generation Hypothesis

Weak Generational Hypothesis: most objects die young Young Generation (Minor GC, fast ~5ms): Eden: new objects allocated here (bump-pointer allocation, O(1)) S0, S1 (Survivor spaces): survive Minor GC, age counter increments → Objects with age ≥ 15 (default): promoted to Old Gen Old Generation (Major/Full GC, slow ~100ms-seconds): Long-lived objects: Spring singleton beans, HikariCP pool, thread-local caches When Old Gen full → Major GC → Stop-The-World! All app threads pause: HTTP requests hang, timeouts cascade G1GC (Java 9+ default): Heap divided into equal regions (~2MB each) Mixed GC: cleans most garbage regions first (highest ROI) Concurrent marking: runs alongside app threads Target: -XX:MaxGCPauseMillis=200 (tries to pause ≤ 200ms) ZGC (Java 15+, ultra-low latency): Pauses < 1ms regardless of heap size Colored pointers: load barriers update references concurrently Trade-off: higher CPU overhead (~15%) for latency guarantee

2. Memory Leaks — How They Happen in Java

// Leak 1: Static collection holding objects
public class MetricRegistry {
    private static final Map<String, Counter> METRICS = new HashMap<>();
    public static void record(String key, Counter c) { METRICS.put(key, c); }
    // Objects in METRICS are GC roots → never collected!
    // If key grows unbounded → OOM
}
// Fix: use weak reference map or bounded cache (Caffeine)

// Leak 2: ThreadLocal not removed
private static final ThreadLocal<UserContext> USER_CTX = new ThreadLocal<>();
// In Tomcat: threads are pooled and REUSED
// If you set ThreadLocal and don't remove: each new request on that thread
// gets PREVIOUS request's data → security leak + memory leak!
try {
    USER_CTX.set(context);
    doWork();
} finally {
    USER_CTX.remove();  // ALWAYS remove in finally!
}

// Leak 3: Hibernate proxy not accessed within session
// Entity with @OneToMany LAZY loaded, session closes, Jackson tries to serialize
// → LazyInitializationException OR holds session open indefinitely

// Leak 4: Listener/Observer not deregistered
eventBus.register(listener);   // listener registered
// Bean destroyed but not unregistered → eventBus holds reference → leak
// Fix: @PreDestroy { eventBus.unregister(this); }

3. Reference Types — GC Interaction

// Strong reference (normal): Object not collected while reference exists
Object obj = new Object();  // strong ref
obj = null;  // eligible for GC now

// SoftReference: collected when JVM needs memory (good for caches)
SoftReference<byte[]> cache = new SoftReference<>(new byte[1024 * 1024]);
byte[] data = cache.get();  // may return null if GC collected it
if (data == null) { data = loadFromDisk(); cache = new SoftReference<>(data); }
// JVM collects SoftRefs before throwing OOM → good for optional caches

// WeakReference: collected on NEXT GC cycle (even without memory pressure)
WeakReference<Session> weakSession = new WeakReference<>(session);
// Used by: ThreadLocal internals, WeakHashMap (key becomes eligible for GC)
// WeakHashMap: when key object is only weakly reachable → entry auto-removed!

// PhantomReference: collected AFTER finalization (rarely used)
// Used for: cleanup actions, replacing finalize()

    }
}

Java Best Practices

1. Immutability — Why It Matters

// Mutable objects: thread-safety issues, unexpected mutations, hard to debug
public class MutableOrder {
    private String status;                       // anyone can change this!
    public void setStatus(String s) { status = s; }
    // Concurrent modification: thread A reads "PENDING"
    // thread B sets "CANCELLED" → thread A proceeds assuming PENDING → bug!
}

// Immutable: once created, cannot change → inherently thread-safe
public final class OrderId {              // final: can't extend
    private final String value;              // final fields: set once in constructor

    public OrderId(String value) {
        this.value = Objects.requireNonNull(value).trim();
        if (value.isEmpty()) throw new IllegalArgumentException("OrderId cannot be empty");
    }
    public String getValue() { return value; }  // getter only, no setter
    // equals/hashCode/toString
}

// Returning defensive copies:
public List<OrderItem> getItems() {
    return List.copyOf(items);  // unmodifiable copy, not view
}
public LocalDate getDeliveryDate() {
    return deliveryDate;  // LocalDate IS immutable, safe to return directly
