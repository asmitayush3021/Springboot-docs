1. Persistence Context — The Heart of JPA

EntityManager = wrapper around Persistence Context (a.k.a. First-Level Cache) ┌──────────────────────────── Persistence Context ──────────────────────────────┐ │ Identity Map: Map<EntityKey, Object> │ │ key = (entity class, primary key) │ │ value = managed entity instance │ │ │ │ Entity States: │ │ TRANSIENT — new object, no ID, PC doesn't know about it │ │ MANAGED — attached to PC, changes tracked by dirty-checking │ │ DETACHED — was managed, PC closed or explicitly detached │ │ REMOVED — scheduled for DELETE on flush │ └───────────────────────────────────────────────────────────────────────────────┘ State transitions: new Order() → TRANSIENT em.persist(order) → MANAGED (INSERT queued) em.find(Order,1L) → MANAGED (loaded from DB or L1 cache) em.detach(order) → DETACHED em.merge(order) → MANAGED (new instance returned, original stays DETACHED) em.remove(order) → REMOVED (DELETE queued) tx.commit() / flush → SQL executed, entity back to MANAGED

Database Transactions — Deep Internals

ACID, isolation, MVCC, locking, deadlocks — from PostgreSQL internals to Spring @Transactional

1. ACID — What Each Property Actually Means

Atomicity

All operations in a TX succeed or all fail. Achieved via Write-Ahead Log (WAL): uncommitted changes in WAL, rollback replays WAL backwards. "All or nothing."

Consistency

DB moves from one valid state to another. Enforced by constraints (FK, NOT NULL, CHECK) + application logic. TX cannot violate defined invariants.

Isolation

Concurrent TXs don't see each other's intermediate states. The hardest property — multiple levels trading isolation for performance.

Durability

Committed TX survives crashes. Achieved via WAL: commit record fsynced to disk before reporting success. Even after power loss, data survives.

2. MVCC — How PostgreSQL Handles Concurrency

PostgreSQL stores multiple versions of each row (no locks for reads): Row in heap: (xmin=100, xmax=0, status='PENDING') ↑ created by TX 100 ↑ not yet deleted TX 200 reads: sees row (xmin=100 ≤ 200, xmax=0) → VISIBLE TX 201 UPDATEs status='SHIPPED': 1. Old row: (xmin=100, xmax=201, status='PENDING') ← mark deleted by TX 201 2. New row: (xmin=201, xmax=0, status='SHIPPED') ← new version TX 200 reads AGAIN (same TX): Old row: xmax=201, TX 201 NOT committed yet → TX 200 still sees xmax=0 version → Reads 'PENDING' (its consistent snapshot) ← REPEATABLE READ guaranteed! TX 201 commits. TX 202 starts, reads: Old row: xmax=201, TX 201 IS committed → NOT visible New row: xmin=201, committed → VISIBLE: 'SHIPPED' Key insight: Readers never block writers, writers never block readers! Dead rows accumulate → VACUUM reclaims them

4. Locking — Row Locks

-- Pessimistic locking: lock rows at SELECT time
BEGIN;
SELECT * FROM inventory WHERE product_id=42 FOR UPDATE;
-- Row locked! Other TXs: SELECT...FOR UPDATE blocks until this TX ends
-- Use for: critical deduction (stock, balance)

UPDATE inventory SET qty = qty - 1 WHERE product_id=42;
COMMIT;

-- FOR UPDATE SKIP LOCKED: queue-like pattern
SELECT * FROM jobs WHERE status='PENDING' LIMIT 1 FOR UPDATE SKIP LOCKED;
-- Returns only unlocked rows → multiple workers process concurrently, no wait

-- Optimistic locking: no DB lock, use version column
UPDATE orders SET status=?, version=version+1 WHERE id=? AND version=?
-- 0 rows updated → someone else changed it → OptimisticLockException
-- Hibernate @Version handles this automatically

Deadlock Detection & Prevention

❌ Deadlock — circular lock wait
-- TX A: locks row 1 then needs row 2
UPDATE accounts SET bal=bal-100 WHERE id=1;
UPDATE accounts SET bal=bal+100 WHERE id=2;

-- TX B (concurrent): locks row 2 then needs row 1
UPDATE accounts SET bal=bal-100 WHERE id=2;
UPDATE accounts SET bal=bal+100 WHERE id=1;
-- DEADLOCK: A waits for B, B waits for A
-- PG detects after ~1s, aborts one TX
✅ Fix: consistent row ordering
// Always lock accounts in ascending ID order
List<Long> ids = Arrays.asList(fromId, toId);
Collections.sort(ids);  // ALWAYS ascending
// Both TXs now lock row 1 first
// TX B waits for TX A to finish row 1
// No circular wait → no deadlock

-- Or: SELECT...FOR UPDATE ORDER BY id
SELECT * FROM accounts WHERE id IN (1,2)
ORDER BY id FOR UPDATE;

Database Indexes — Internals & Query Optimization

B-tree, Hash, GIN, GiST, BRIN — with EXPLAIN ANALYZE and real benchmarks

1. B-Tree Index — The Universal Index

B-Tree structure (PostgreSQL): Root Page [25 | 50 | 75] / | \ Internal Internal Internal [10|15|20] [30|40|45] [60|65|70] / | | \ Leaf Leaf Leaf Leaf ← leaf pages doubly linked ↔ [8,9] [10,11] [12] [13,14] (range scans traverse chain) ↓ ↓ ↓ ↓ heap heap heap heap ← TID (table ID + page + offset) Operations: Point query (WHERE id=42): O(log n) ~3-4 page reads for 1M rows Range query (WHERE id>40): O(log n + k) find start, follow leaf chain Sort (ORDER BY id): FREE — already sorted in leaf chain

Composite Index — Column Order Matters

-- Index: (status, created_at)
CREATE INDEX idx_orders_status_created ON orders(status, created_at DESC);

-- ✅ Uses index: leftmost prefix rule
SELECT * FROM orders WHERE status='PENDING';              -- uses status prefix
SELECT * FROM orders WHERE status='PENDING' ORDER BY created_at DESC; -- perfect match
SELECT * FROM orders WHERE status='PENDING' AND created_at > '2024-01-01'; -- both columns

-- ❌ Does NOT use index: skips leading column
SELECT * FROM orders WHERE created_at > '2024-01-01'; -- no status filter → seq scan

-- Rule: put equality columns first, range columns last
-- (status='X' AND created_at > Y) → (status, created_at) ✅
-- (customer_id=X AND status='Y') → (customer_id, status) ✅

1. PostgreSQL Streaming Replication

Primary (Leader) │ Accepts: reads + writes │ WAL (Write-Ahead Log): changes written here first │ ├─ WAL Sender process ──── WAL stream ────▶ Standby-1 (WAL Receiver) │ Applies WAL → same state as primary │ Can serve: read-only SELECTs │ └─ WAL Sender process ──── WAL stream ────▶ Standby-2 (async by default) Synchronous replication: PRIMARY waits for at least N standbys to confirm WAL received before commit synchronous_standby_names = 'FIRST 1 (standby1, standby2)' → Zero data loss on failover (RPO=0) but higher write latency Asynchronous replication (default): PRIMARY commits immediately, standbys lag behind Replication lag: seconds to minutes under load Risk: failover may lose recent writes (RPO > 0)

2. Sharding Strategies

-- Range sharding: partition by value range
-- Shard 1: customer_id 1-1,000,000
-- Shard 2: customer_id 1,000,001-2,000,000
-- Shard 3: customer_id 2,000,001+

-- Pro: range queries are shard-local, ordered scans efficient
-- Con: HOT SPOTS — new users always go to last shard
-- Con: shard rebalancing required as data grows
-- Use case: time-series partitioning by date range (natural ordering)

-- PostgreSQL range partitioning:
CREATE TABLE orders (id BIGINT, created_at TIMESTAMPTZ, ...)
PARTITION BY RANGE (created_at);
CREATE TABLE orders_2024_q1 PARTITION OF orders
  FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');
CREATE TABLE orders_2024_q2 PARTITION OF orders
  FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');
-- Hash sharding: shard = hash(key) % num_shards
shard_id = SHA256(customer_id) % 8  -- 8 shards

-- Pro: even distribution, no hot spots
-- Con: range queries span all shards (scatter-gather)
-- Con: resharding is painful (consistent hashing mitigates)
-- Use case: user data, session data — mostly point lookups

-- Consistent hashing: virtual nodes on ring
-- Adding shard: only move ~1/N of data
-- Removing shard: only reassign that shard's data
-- Libraries: ketama, jump consistent hash

-- PostgreSQL hash partitioning:
CREATE TABLE users PARTITION BY HASH (id);
CREATE TABLE users_0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE users_1 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- Directory/Lookup sharding: central mapping table

3. Cross-Shard Query Problems

Problem 1: Cross-shard JOIN SELECT o.*, u.name FROM orders o JOIN users u ON u.id=o.user_id → orders on shard 1, user on shard 3 → IMPOSSIBLE efficiently Solution: denormalize user_name into orders at write time Problem 2: Global aggregation SELECT COUNT(*) FROM orders WHERE status='PENDING' → must query ALL shards and sum results (scatter-gather) Solution: maintain global counter in Redis; or async materialized view Problem 3: Distributed transactions Transfer money: debit shard-1, credit shard-3 → atomicity? Solution 1: Two-Phase Commit (slow, blocks) Solution 2: SAGA pattern (eventual consistency) Solution 3: Move both accounts to same shard (co-location)

Redis Internals

Memory model, persistence, eviction, data structures, pub/sub, streams, scaling

1. Redis Memory Architecture

Single-threaded event loop (I/O + commands): epoll/kqueue → multiple connections monitored One command executes at a time → no data races, no locks! Multi-threading added in Redis 6+ for I/O only (parsing, writes) Main command execution: still single-threaded Memory layout: jemalloc allocator → minimize fragmentation Dict (hash table): global keyspace key → Redis Object (type, encoding, refcount, lru_clock, ptr) Encodings (auto-selected for space efficiency): String: int (≤20 char number), embstr (≤44 bytes), raw (larger) List: listpack (≤128 elements, ≤64 bytes) → quicklist (doubly-linked of listpacks) Hash: listpack (≤128 fields) → hashtable Set: listpack / intset → hashtable ZSet: listpack (≤128 members) → skiplist + hashtable Stream: radix tree of listpack nodes

2. Cache Stampede (Thundering Herd) — Prevention

❌ Stampede: all threads miss simultaneously
// Cache for popular product expires at 12:00:00
// 1000 requests arrive at 12:00:00.001
// ALL see cache miss
// ALL query DB simultaneously
// DB receives 1000 concurrent queries
// DB overloaded → slow → more requests pile up
// → cascading failure!
✅ Mutex lock on cache miss
public ProductDto getProduct(Long id) {
    ProductDto cached = redis.get("product:"+id);
    if (cached != null) return cached;

    String lockKey = "lock:product:"+id;
    // Only ONE thread rebuilds cache
    if (redis.setIfAbsent(lockKey,"1",Duration.ofSeconds(10))) {
        try {
            ProductDto data = db.findProduct(id);
            redis.set("product:"+id, data, Duration.ofHours(1));
            return data;
        } finally { redis.delete(lockKey); }
    }
    Thread.sleep(50); return getProduct(id); // retry
}
// Better: Probabilistic Early Expiration (PER)
// Slightly before TTL expires, proactively recompute
public ProductDto getWithEarlyRecompute(Long id) {
    CacheEntry<ProductDto> entry = redis.getCacheEntry("product:"+id);
    if (entry != null) {
        double ttlRemaining = entry.getTtlSeconds();
        double delta = entry.getComputeTime() * 1.5;
        // Recompute early with probability proportional to remaining TTL
        if (ttlRemaining > delta || Math.random() > Math.exp(-delta/ttlRemaining)) {
            return entry.getValue();  // serve stale value
        }
    }
    return recomputeAndCache(id);  // proactive recompute
}

Distributed Locks

SETNX, TTL pitfalls, Redlock, Redisson, booking system examples

1. Why Distributed Locks Are Hard

Problem: Two instances, same operation simultaneously Instance A: check seat available (yes) Instance B: check seat available (yes) ← race condition Instance A: reserve seat Instance B: reserve seat ← DOUBLE BOOKING! Wrong solution: Simple SETNX SET lock:seat:42 1 ← acquired lock (instance crashes here!) lock never released → seat locked forever ← no TTL = deadlock Better but still wrong: SETNX + EXPIRE (two commands) SET lock:seat:42 1 ← success (crash between commands!) EXPIRE lock:seat:42 10 ← never executes → deadlock! Correct: Atomic SET NX PX SET lock:seat:42 {uuid} NX PX 10000 ← atomic: set IF NOT EXISTS with 10s TTL

2. Correct Single-Redis Lock Implementation

@Service
public class SeatReservationService {
    private final StringRedisTemplate redis;
    private static final String LOCK_PREFIX = "lock:seat:";

    public boolean reserveSeat(Long seatId, Long userId) {
        String lockKey = LOCK_PREFIX + seatId;
        String lockValue = UUID.randomUUID().toString();  // unique per holder

        // Atomic: SET key value NX PX 10000
        Boolean acquired = redis.opsForValue().setIfAbsent(
            lockKey, lockValue, Duration.ofSeconds(10));

        if (!Boolean.TRUE.equals(acquired)) {
            throw new ConflictException("Seat "} + seatId + " is being processed");
        }

        try {
            // Critical section — only ONE instance here at a time
            Seat seat = seatRepo.findById(seatId).orElseThrow();
            if (seat.isReserved()) throw new ConflictException("Already reserved");
            seat.reserve(userId);
            seatRepo.save(seat);
            return true;
        } finally {
            // CRITICAL: only release OUR lock (compare-and-delete via Lua)
            releaseLock(lockKey, lockValue);
        }
    }

    private void releaseLock(String key, String expectedValue) {
        String luaScript = """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end""";  // Atomic compare-and-delete! Prevents releasing someone else's lock
        redis.execute(new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(key), expectedValue);
    }
}

@Service
public class PaymentService {
    private final RedissonClient redisson;

    public PaymentResult processPayment(String orderId, BigDecimal amount) {
        RLock lock = redisson.getLock("payment:lock:" + orderId);
        try {
            // Wait up to 5s to acquire, hold for max 30s (watchdog auto-renews)
            if (!lock.tryLock(5, 30, TimeUnit.SECONDS)) {
                throw new ConcurrentPaymentException("Payment already in progress");
            }
            return doProcessPayment(orderId, amount);
        } finally {
            if (lock.isHeldByCurrentThread()) lock.unlock();
        }
    }

    // Redisson features:
    // Watchdog: auto-extends TTL every 10s while locked (prevents expiry during work)
    // Reentrant: same thread can lock multiple times
    // Fair lock: FIFO ordering (RLock fairLock = redisson.getFairLock(key))
    // Read-Write lock: multiple readers OR one writer

4. Redlock Algorithm (Multi-Node)

Redlock: acquire on majority of N independent Redis nodes N = 5 nodes (or 3 for lower safety) Algorithm: 1. Get current time T1 2. Try SET key value NX PX ttl on ALL 5 nodes (in parallel) 3. Count successes: must be ≥ 3 (majority) 4. Elapsed = now() - T1 5. If successes ≥ 3 AND elapsed < ttl → lock acquired! Remaining validity = ttl - elapsed 6. If failed: DEL key on ALL nodes that succeeded Why single-node fails: Node crashes after SET, before response → lock lost, timeout only exit Network partition: client thinks lock acquired, another client too → split-brain Redlock controversy (Martin Kleppmann): Process pauses (GC, VM) between acquire and use → lock expired, another acquired Fix: use fencing tokens (monotonic counter from Zookeeper) for resource access → Even if two clients hold the lock, lower token is rejected by resource

@Component

    @KafkaListener(
        topics = "orders",
        groupId = "order-processor",
        concurrency = "3"    // 3 consumer threads per instance
    )
    public void consume(
            ConsumerRecord<String, OrderEvent> record,
            Acknowledgment ack) {  // manual ack mode

        MDC.put("traceId", new String(record.headers().lastHeader("traceId").value()));
        try {
            log.info("Processing offset={} partition={} key={}",
                record.offset(), record.partition(), record.key());
            orderService.process(record.value());
            ack.acknowledge();  // commit offset AFTER successful processing
        } catch (RetryableException e) {
            // Don't ack → Kafka will redeliver
            throw e;
        } catch (FatalException e) {
            ack.acknowledge();  // ack to skip + send to DLQ manually
            deadLetterService.send(record, e);
        } finally {
            MDC.clear();
        }
    }
}

// Aggregate — state rebuilt from events
public class Order {
    private String id;
    private OrderStatus status;
    private BigDecimal amount;
    private final List<DomainEvent> pendingEvents = new ArrayList<>();

    // Create from events (reconstitution)
    public static Order reconstitute(List<DomainEvent> events) {
        Order order = new Order();
        events.forEach(order::apply);
        return order;
    }

    // Command handler produces events
    public void place(String customerId, List<Item> items) {
        if (status != null) throw new IllegalStateException("Already placed");
        apply(new OrderPlacedEvent(id, customerId, items, Instant.now()));
    }

    public void ship(String trackingId) {
        if (status != OrderStatus.PAID) throw new IllegalStateException();
        apply(new OrderShippedEvent(id, trackingId, Instant.now()));
    }

    // Apply event: mutate state + record pending
    private void apply(DomainEvent event) {
        pendingEvents.add(event);  // to be persisted
        when(event);               // update in-memory state
    }

    // Event handler — pure state mutation
    private void when(DomainEvent event) {
        switch (event) {
            case OrderPlacedEvent e   -> { status = PENDING; amount = e.getAmount(); }
            case PaymentReceivedEvent e -> status = PAID;
            case OrderShippedEvent e   -> status = SHIPPED;
            case OrderCancelledEvent e -> status = CANCELLED;
            default -> {}
        }
    }
}

// Event Store repository
@Repository
public class EventStoreRepository {

    @Transactional
    public void save(Order order) {
        List<DomainEvent> events = order.getPendingEvents();
        for (DomainEvent event : events) {
            EventRecord record = EventRecord.builder()
                .aggregateId(order.getId())
                .aggregateType("Order")
                .eventType(event.getClass().getSimpleName())
                .eventData(objectMapper.writeValueAsString(event))
                .sequenceNumber(nextSequence(order.getId()))
                .occurredAt(event.getOccurredAt())
                .build();
            jdbcTemplate.update(
                "INSERT INTO event_store (aggregate_id, aggregate_type, event_type, event_data, seq) VALUES (?,?,?,?,?)",
                record.getAggregateId(), record.getAggregateType(),
                record.getEventType(), record.getEventData(), record.getSeq());
        }
        // publish to Kafka for projections
        events.forEach(kafkaTemplate::send.apply("order-events"));
        order.clearPendingEvents();
    }

    public Order load(String orderId) {
        List<EventRecord> records = jdbcTemplate.query(
            "SELECT * FROM event_store WHERE aggregate_id=? ORDER BY seq",
            eventRecordMapper, orderId);
        List<DomainEvent> events = records.stream()
            .map(this::deserialize).toList();
        return Order.reconstitute(events);
    }
}

Transactional Outbox Pattern

Dual-write problem, exactly-once publishing, Debezium CDC, Spring Boot

1. The Dual-Write Problem

Problem: DB and Kafka are separate systems → no distributed transaction Option A: Save to DB, then publish to Kafka @Transactional { orderRepo.save(order); ← DB commit succeeds } kafkaTemplate.send(orderEvent); ← Kafka FAILS! Event never published. Result: Order saved but no downstream processing! Option B: Publish to Kafka, then save to DB kafkaTemplate.send(orderEvent); ← Kafka succeeds @Transactional { orderRepo.save(order); ← DB FAILS! Transaction rolled back. } Result: Event published but no order in DB! Ghost event. Solution: Outbox Pattern @Transactional { orderRepo.save(order); ← DB outboxRepo.save(orderEvent); ← SAME transaction, same DB! } ← Both committed atomically (Separate relay: read outbox → publish to Kafka → delete from outbox)

2. Outbox Table + Relay Implementation

@Transactional

        .eventType("OrderPlaced")
        .payload(objectMapper.writeValueAsString(OrderPlacedEvent.from(order)))

}

// Polling relay (simple but introduces latency)
@Scheduled(fixedDelay = 1000)  // every 1 second
@Transactional
public void publishOutboxEvents() {
    List<OutboxEvent> pending = outboxRepo
        .findTop100ByProcessedAtIsNullOrderByCreatedAt();

    pending.forEach(event -> {
        try {
            kafkaTemplate.send("orders", event.getAggregateId(), event.getPayload()).get();
            event.markProcessed();
            outboxRepo.save(event);
        } catch (Exception e) {
            event.incrementAttempts();
            if (event.getAttempts() > 5) event.markFailed();
            outboxRepo.save(event);
        }
    });
}

SAGA Pattern

Orchestration vs choreography, compensating transactions, booking/payment workflows

1. Why SAGA — Distributed Transactions Without 2PC

2-Phase Commit (2PC) problems: Phase 1: Coordinator asks all participants "can you commit?" → all lock resources Phase 2: Coordinator says "commit" or "abort" → Coordinator crash after Phase 1 = all participants BLOCKED forever → Synchronous blocking → poor availability SAGA: sequence of local transactions with compensations Each step: local TX + event/command to next step On failure: run compensating transactions backwards No global lock, eventual consistency Hotel Booking SAGA: Step 1: Reserve hotel → success → HotelReserved event Step 2: Charge payment → success → PaymentCharged event Step 3: Confirm booking → success → BookingConfirmed event Failure at Step 3: Compensate Step 2: Refund payment Compensate Step 1: Cancel hotel reservation

2. Choreography SAGA (Event-Driven)

// Each service listens for events, acts, publishes next event

@Service
public class OrderSaga {
    @Transactional
    public void createOrder(CreateOrderRequest req) {
        Order order = orderRepo.save(Order.create(req));
        outbox.save(new OrderPlacedEvent(order));  // step 1
    }
}

// 2. InventoryService listens, reserves stock
@KafkaListener(topics = "order-placed")
@Transactional
public void onOrderPlaced(OrderPlacedEvent event) {
    try {
        inventoryService.reserve(event.getItems());
        outbox.save(new StockReservedEvent(event.getOrderId()));  // step 2
    } catch (InsufficientStockException e) {
        outbox.save(new StockReservationFailedEvent(event.getOrderId()));  // compensate
    }
}

// 3. PaymentService listens to StockReserved
@KafkaListener(topics = "stock-reserved")
@Transactional
public void onStockReserved(StockReservedEvent event) {
    try {
        paymentService.charge(event.getOrderId(), event.getAmount());
        outbox.save(new PaymentChargedEvent(event.getOrderId()));
    } catch (PaymentFailedException e) {
        outbox.save(new PaymentFailedEvent(event.getOrderId()));  // compensation trigger
    }
}

// Compensation: InventoryService listens for PaymentFailed
@KafkaListener(topics = "payment-failed")
@Transactional
public void onPaymentFailed(PaymentFailedEvent event) {
    inventoryService.releaseReservation(event.getOrderId());  // compensate step 2
    outbox.save(new StockReleasedEvent(event.getOrderId()));
}
// Con: hard to visualize flow, debugging is complex, event explosion

3. Orchestration SAGA (Central Coordinator)

// Central saga orchestrator drives the workflow
@Component
public class BookingOrchestrator {

    public BookingSaga start(BookingRequest req) {
        BookingSaga saga = BookingSaga.builder()
            .sagaId(UUID.randomUUID().toString())
            .state(STARTED)
            .request(req)
            .build();
        sagaRepo.save(saga);
        // Execute step 1
        executeStep(saga, RESERVE_HOTEL);
        return saga;
    }

    public void handleEvent(SagaEvent event) {
        BookingSaga saga = sagaRepo.findBySagaId(event.getSagaId());

        switch (saga.getState()) {
            case RESERVE_HOTEL_PENDING -> {
                if (event instanceof HotelReservedEvent) {
                    saga.setState(CHARGE_PAYMENT_PENDING);
                    executeStep(saga, CHARGE_PAYMENT);
                } else if (event instanceof HotelReservationFailedEvent) {
                    saga.setState(FAILED);  // nothing to compensate
                }
            }
            case CHARGE_PAYMENT_PENDING -> {
                if (event instanceof PaymentChargedEvent) {
                    saga.setState(COMPLETED);
                } else if (event instanceof PaymentFailedEvent) {
                    // Run compensation
                    saga.setState(COMPENSATING);
                    compensateStep(saga, CANCEL_HOTEL_RESERVATION);
                }
            }
            case COMPENSATING -> {
                if (event instanceof HotelCancelledEvent) {
                    saga.setState(COMPENSATED);
                }
            }
        }
        sagaRepo.save(saga);
    }
}
// Pro: central visibility, easy debugging, clear state machine
// Con: orchestrator can be bottleneck, coupling of services

Microservices Architecture

Domain decomposition, communication, discovery, tracing, operational complexity

1. When to Use Microservices

❌ Microservices too early
// Premature decomposition:
// UserService, ProductService, OrderService
// all in separate services from day 1
// Team: 3 developers
// Result:
// - 3x deployment overhead
// - Distributed transactions everywhere
// - Network failures between services
// - 3x monitoring to set up
// - 0x business value added
✅ Monolith first, extract when justified
// Start: well-structured monolith
// Extract when:
// - Different scaling needs (Payment vs Search)
// - Different deployment cadence
// - Different tech stack required
// - Team ownership boundaries clear
// - Bounded context is stable
// Rule: extract service only when pain
// of NOT extracting exceeds the cost

2. DDD Bounded Contexts → Services

E-Commerce Domain → Bounded Contexts: Order Context: OrderService (PostgreSQL) Order, OrderItem, OrderStatus Catalog Context: ProductService (PostgreSQL + Elasticsearch) Product, Category, Inventory Payment Context: PaymentService (PostgreSQL, PCI-DSS zone) Payment, Transaction, Refund Identity Context: UserService (PostgreSQL + Redis) User, Role, Session, OAuth Notification Context: NotificationSvc (MongoDB, separate scaling) Email, SMS, Push templates Anti-patterns to avoid: Shared database between services → tight coupling, defeats the purpose Synchronous calls for every operation → high coupling, cascading failures Distributed transactions across services → use SAGA instead

Resilience Patterns

Circuit breaker, retry, bulkhead, rate limit, timeout — with Resilience4J + Spring Boot

1. Circuit Breaker — Fail Fast

States: CLOSED → requests pass through normally OPEN → all requests fail immediately (circuit broken) — recovery wait HALF_OPEN → probe requests allowed (N calls), if succeed → CLOSED Transition: CLOSED → OPEN: failure rate ≥ threshold (e.g., 50% in last 10 calls) OPEN → HALF_OPEN: after waitDurationInOpenState (60s) HALF_OPEN → CLOSED: probe calls succeed (permittedCallsInHalfOpenState = 3) HALF_OPEN → OPEN: probe calls fail Why it helps: Without CB: 10,000 threads wait 30s for timeout → system dead With CB: after 5 failures → OPEN → fail in 1ms → threads freed immediately

2. Resilience4J — Full Configuration

# application.yml
resilience4j:
  circuitbreaker:
    instances:
      payment-service:
        slidingWindowSize: 10           # evaluate last 10 calls
        minimumNumberOfCalls: 5         # minimum before opening
        failureRateThreshold: 50        # open if 50%+ fail
        waitDurationInOpenState: 60s
        permittedNumberOfCallsInHalfOpenState: 3
        recordExceptions:
          - java.net.ConnectException
          - java.util.concurrent.TimeoutException
        ignoreExceptions:
          - com.example.BusinessException  # don't count business errors

  retry:
    instances:
      payment-service:
        maxAttempts: 3
        waitDuration: 1s
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2  # 1s, 2s, 4s
        retryExceptions:
          - java.net.ConnectException
          - org.springframework.web.client.HttpServerErrorException

  bulkhead:
    instances:
      inventory-service:
        maxConcurrentCalls: 10          # max parallel calls
        maxWaitDuration: 500ms

  timelimiter:
    instances:
      external-api:
        timeoutDuration: 3s
@Service
public class PaymentGatewayClient {

    @CircuitBreaker(name = "payment-service", fallbackMethod = "paymentFallback")
    @Retry(name = "payment-service")
    @Bulkhead(name = "payment-service", type = Bulkhead.Type.SEMAPHORE)
    @TimeLimiter(name = "payment-service")
    public CompletableFuture<PaymentResult> charge(PaymentRequest req) {
        return CompletableFuture.supplyAsync(
            () -> restTemplate.postForObject(
                "http://payment-service/charge", req, PaymentResult.class));
    }

    public CompletableFuture<PaymentResult> paymentFallback(
            PaymentRequest req, Throwable t) {
        log.warn("Payment service unavailable: {}", t.getMessage());
        return CompletableFuture.completedFuture(
            PaymentResult.pending(req.getOrderId()));  // queue for retry
    }
}

3. Rate Limiting with Bucket4j

@Component
public class RateLimitFilter implements HandlerInterceptor {

    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        String clientId = extractClientId(req);
        Bucket bucket = buckets.computeIfAbsent(clientId, k -> Bucket.builder()
            .addLimit(Bandwidth.classic(100, Refill.greedy(100, Duration.ofMinutes(1))))
            .build());

        ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) {
            res.addHeader("X-Rate-Limit-Remaining", String.valueOf(probe.getRemainingTokens()));
            return true;
        }
        res.setStatus(429);
        res.addHeader("X-Rate-Limit-Retry-After-Seconds",
            String.valueOf(probe.getNanosToWaitForRefill() / 1_000_000_000));
        return false;
    }
}

API Gateway

Routing, auth, throttling, aggregation, observability — Spring Cloud Gateway

1. API Gateway Responsibilities

Routing & Load Balancing

Route requests to correct microservice based on path, method, headers. Load balance across instances. Path rewriting.

Authentication & Authorization

Validate JWT tokens at gateway level. Strip auth headers before forwarding. Single auth enforcement point.

Rate Limiting

Per-client, per-IP, per-endpoint rate limits. Redis-backed distributed counters. Return 429 with Retry-After.

Request Aggregation

Compose response from multiple services. Parallel fanout. Merge results. Reduces client round-trips.

Observability

Centralized logging with traceId. Request/response timing. Upstream error aggregation. Metrics.

SSL Termination

HTTPS at gateway. Internal services use plain HTTP. Centralized certificate management.

3. JWT Validation at Gateway

@Component
public class JwtAuthFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();

        // Skip auth for public endpoints
        if (path.startsWith("/api/auth/") || path.startsWith("/actuator/")) {
            return chain.filter(exchange);
        }

        String authHeader = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        return jwtService.validateToken(authHeader.substring(7))
            .flatMap(claims -> {
                ServerHttpRequest mutated = exchange.getRequest().mutate()
                    .header("X-User-Id", claims.getSubject())
                    .header("X-User-Roles", String.join(",", claims.getRoles()))
                    .build();
                // Downstream services read X-User-Id header (no JWT re-validation)
                return chain.filter(exchange.mutate().request(mutated).build());
            })
            .onErrorResume(e -> {
                exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
                return exchange.getResponse().setComplete();
            });
    }

    @Override
    public int getOrder() { return -100; }  // very high priority
}

// Downstream service extracts user from header (no JWT library needed):

}

4. Request Aggregation — BFF Pattern

// Backend for Frontend: aggregate multiple service calls
@RestController
public class DashboardAggregator {

    @GetMapping("/api/dashboard")
    public Mono<DashboardDto> getDashboard(@RequestHeader("X-User-Id") String userId) {
        Mono<UserDto> user = webClient.get()
            .uri("http://user-service/users/{id}", userId).retrieve()
            .bodyToMono(UserDto.class).timeout(Duration.ofSeconds(2));

        Mono<List<OrderDto>> orders = webClient.get()
            .uri("http://order-service/orders?userId={id}&limit=5", userId).retrieve()
            .bodyToFlux(OrderDto.class).collectList().timeout(Duration.ofSeconds(2));

        Mono<List<NotificationDto>> notifications = webClient.get()
            .uri("http://notification-service/notifications/{id}", userId).retrieve()
            .bodyToFlux(NotificationDto.class).collectList()
            .timeout(Duration.ofSeconds(2))
            .onErrorReturn(Collections.emptyList());  // degrade gracefully

        // Execute all in PARALLEL via reactive zip
        return Mono.zip(user, orders, notifications)
            .map(tuple -> DashboardDto.of(tuple.getT1(), tuple.getT2(), tuple.getT3()));
        // Total time = max(2s, 2s, 2s) = 2s  (not 6s sequential!)
    }
}
💡 Gateway Anti-Patterns
Don't put business logic in the gateway — it becomes a bottleneck and coupling point. The gateway should be thin: auth, routing, rate limiting, logging. All business logic stays in services. If the gateway needs to understand domain objects, it has too much responsibility.
