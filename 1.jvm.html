2. Class Loading Subsystem

🔵 Bootstrap CL

Loads java.lang.*, java.util.* from rt.jar / modules. Written in native C. Parent of all.

🟡 Extension / Platform CL

Loads javax.*, security, XML. Java 9+: Platform ClassLoader handles named modules.

🟢 App ClassLoader

Loads your app's classpath. Spring Boot's LaunchedURLClassLoader wraps this for nested JARs.

Delegation Model (Parent-First)

AppClassLoader.loadClass("com.example.Service") → ask Bootstrap → not found → ask Extension → not found → load itself → found! return Class object

Class Loading Phases

JVM reads .class bytes, creates java.lang.Class object in heap, stores metadata in Metaspace.

// Spring Boot: LaunchedURLClassLoader reads from nested JAR
// BOOT-INF/classes/ + BOOT-INF/lib/*.jar
protected Class<?> findClass(String name) throws ClassNotFoundException {
    // opens nested URL connection
    // reads .class bytes
    return defineClass(name, bytes, 0, bytes.length);
}

Three sub-phases: Verification (bytecode safety), Preparation (static field defaults), Resolution (symbolic refs → direct refs).

// Preparation: static fields get DEFAULT values
class AppConfig {
    static int MAX = 100;   // Preparation: MAX = 0
    // then Initialization sets MAX = 100
}

Static initializers run once, thread-safely. Spring beans initialized after this.

class DatabasePool {
    static final ConnectionPool POOL;
    static {
        // runs ONCE, JVM guarantees thread-safety
        POOL = new ConnectionPool(20);
        System.out.println("Pool initialized");
    }
}

Heap: Young vs Old Generation

🌱 Young Generation (Minor GC)
Eden ──[full]──▶ Minor GC
├── live objects ──▶ Survivor S0
└── dead objects ──▶ collected

S0 ──[age≥15]──▶ promoted to Old
S0 ──▶ S1 (swap each minor GC)

Spring: Most request objects die here
Minor GC: ~1-10ms, very frequent
🏔️ Old Generation (Major/Full GC)
Survivors promoted from Young
Long-lived objects:
  - Spring singleton beans
  - Caches (Caffeine, Redis client)
  - Thread pools
  - Connection pools (HikariCP)

Major GC: ~100ms-seconds
Stop-The-World = app pauses!

4. JIT Compiler

Interpreted (slow) │ │ ~1000 invocations ▼ C1 Compiler (Client) — fast compile, light optimizations │ │ ~10000 invocations (hotspot threshold) ▼ C2 Compiler (Server) — aggressive: inlining, escape analysis, loop unrolling │ │ profile-guided ▼ Native Machine Code (fastest)

Key JIT Optimizations

Method Inlining
// Before JIT:
result = add(a, b);

// After inline:
result = a + b;
// call overhead removed
// Spring: getters inlined!
Escape Analysis
// Object doesn't escape
// method → stack allocated!
Point p = new Point(x,y);
return p.x + p.y;
// p never goes to heap
// no GC pressure
Loop Unrolling
// Before:
for(i=0; i<4; i++) sum+=a[i];

// After JIT:
sum = a[0]+a[1]+a[2]+a[3];
// branch removed

3. Synchronization & Race Conditions

❌ Race Condition — BROKEN
@Service
public class CounterService {
    private int count = 0; // NOT thread-safe

    public void increment() {
        count++;  // READ-MODIFY-WRITE
        // NOT atomic! 3 bytecode ops:
        // getfield, iadd, putfield
        // Two threads can interleave!
    }
}
// Result: 10000 increments
// Expected: 10000, Actual: ~9800
✅ Fixed Options
// Option 1: synchronized
public synchronized void increment() {
    count++;
}

// Option 2: AtomicInteger (preferred)
private AtomicInteger count =
    new AtomicInteger(0);
public void increment() {
    count.incrementAndGet(); // CAS op
}

// Option 3: LongAdder (high contention)
private LongAdder count = new LongAdder();
public void increment() { count.increment(); }

The volatile Keyword

public class ShutdownExample {
    // Without volatile: thread may cache in register!
    // Other thread's write never seen → infinite loop
    private volatile boolean running = true;

    public void stop() {
        running = false;  // write visible to ALL threads immediately
    }

    public void run() {
        while (running) {  // always reads from main memory
            processNextTask();
        }
    }
}
// volatile: visibility guarantee, NOT atomicity
// volatile++ is still NOT atomic!

4. Deadlock — Detection & Prevention

❌ Classic Deadlock
// Thread 1: locks A then B
// Thread 2: locks B then A
// → Circular wait = deadlock

synchronized(lockA) {
    Thread.sleep(50);
    synchronized(lockB) {  // waits for B
        doWork();
    }
}

// Meanwhile Thread 2:
synchronized(lockB) {
    Thread.sleep(50);
    synchronized(lockA) {  // waits for A
        doWork();          // DEADLOCK!
    }
}
✅ Prevention: Lock Ordering
// ALWAYS lock in same order!
private static final Object LOCK_A = new Object();
private static final Object LOCK_B = new Object();

// Both threads: A then B, always
synchronized(LOCK_A) {
    synchronized(LOCK_B) {
        doWork();
    }
}

// Or use tryLock with timeout:
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { doWork(); }
    finally { lock.unlock(); }
} else { /* timeout, retry/fail */ }
🔍 Detect deadlocks
jstack <pid> | grep -A 20 "deadlock" — JVM prints deadlock info automatically. In Spring Boot Actuator: /actuator/threaddump

5. Thread Pools Deep Dive

ThreadPoolExecutor Internals

// Spring's @Async uses this under the hood
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    5,          // corePoolSize:  always alive
    20,         // maximumPoolSize: created under load
    60L, TimeUnit.SECONDS,  // keepAlive for above-core threads
    new LinkedBlockingQueue<>(100),  // task queue capacity
    new ThreadPoolExecutor.CallerRunsPolicy() // rejection policy
);

// Task submission flow:
// 1. Pool < core?         → create new thread
// 2. Queue not full?      → enqueue task
// 3. Pool < max?          → create new thread
// 4. Queue full + at max? → RejectionHandler!

Spring Boot @Async Configuration

@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean("emailExecutor")
    public TaskExecutor emailExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(500);
        executor.setThreadNamePrefix("Email-");
        executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}

@Service
public class EmailService {

    @Async("emailExecutor")
    public CompletableFuture<Void> sendWelcomeEmail(String email) {
        // runs in Email-1..10 thread, not HTTP thread
        sendSMTP(email);
        return CompletableFuture.completedFuture(null);
    }
}

6. CompletableFuture — Async Pipelines

Real Spring Boot Example: Parallel API Calls

@Service
public class ProductService {

    public ProductDetail getProductDetail(long id) {
        // Sequential: 300ms + 200ms = 500ms
        // Parallel:   max(300ms, 200ms) = 300ms

        CompletableFuture<Product> productFuture =
            CompletableFuture.supplyAsync(
                () -> productRepo.findById(id),
                executor  // custom pool, not ForkJoin!
            );

        CompletableFuture<List<Review>> reviewsFuture =
            CompletableFuture.supplyAsync(
                () -> reviewService.getReviews(id),
                executor
            );

        CompletableFuture<Inventory> inventoryFuture =
            CompletableFuture.supplyAsync(
                () -> inventoryService.getStock(id),
                executor
            );

        // Wait for ALL to complete
        CompletableFuture.allOf(productFuture, reviewsFuture, inventoryFuture)
            .join(); // blocks current thread max until all done

        return new ProductDetail(
            productFuture.join(),
            reviewsFuture.join(),
            inventoryFuture.join()
        );
    }
}

CompletableFuture Chaining

CompletableFuture
    .supplyAsync(() -> fetchUser(userId))    // async: returns User
    .thenApply(user -> enrichUser(user))     // sync transform
    .thenCompose(user -> fetchOrders(user))  // async flatMap
    .thenAccept(orders -> saveToCache(orders))// consume, no return
    .exceptionally(ex -> {
        log.error("Pipeline failed", ex);
        return null;                         // fallback
    })
    .orTimeout(5, TimeUnit.SECONDS);        // Java 9+ timeout

7. Virtual Threads (Java 21 + Spring Boot 3.2)

## application.properties
spring.threads.virtual.enabled=true

// What changes:
// Platform thread: OS thread, 1MB stack, expensive
// Virtual thread: JVM-managed, ~few KB, millions possible

// BEFORE (blocks OS thread during DB query):
// Worker-23 is parked → OS thread wasted

// AFTER (virtual thread unmounts from OS thread during I/O):
// Virtual-T-23 waiting for DB
// OS carrier thread picks up DIFFERENT virtual thread
// No blocking! 10x throughput improvement for I/O apps

// WARNING: Don't pool virtual threads!
// ❌ new ThreadPoolExecutor(200, 200, ...)
// ✅ Executors.newVirtualThreadPerTaskExecutor()
⚠️ Common Mistakes
ThreadLocal with virtual threads: ThreadLocal leaks between tasks if using thread pools. Use ScopedValue (Java 21 preview) instead.

synchronized + virtual threads: synchronized pins virtual thread to carrier OS thread. Use ReentrantLock instead for virtual-thread-safe code.

Singleton Pattern

Ensure a class has exactly one instance. Creational

Thread-Safe Implementations

// ✅ BEST: Enum Singleton - JVM guarantees uniqueness
public enum DatabaseConfig {
    INSTANCE;

    private final String url;
    private final int maxConnections;

    DatabaseConfig() {
        // initialized once, thread-safe by JVM
        this.url = System.getenv("DB_URL");
        this.maxConnections = 20;
    }

    public String getUrl() { return url; }
    public int getMaxConnections() { return maxConnections; }
}

// Usage:
DatabaseConfig.INSTANCE.getUrl()
// Serialization-safe, reflection-safe
public class AppRegistry {
    // volatile: prevents CPU reordering
    private static volatile AppRegistry instance;

    private AppRegistry() {
        // private constructor
    }

    public static AppRegistry getInstance() {
        if (instance == null) {        // first check (no lock)
            synchronized(AppRegistry.class) {
                if (instance == null) { // second check (locked)
                    instance = new AppRegistry();
                }
            }
        }
        return instance;
    }
}
// volatile is CRITICAL: without it, another thread
// may see a partially constructed object!
// ❌ BROKEN: Not thread-safe!
public class BrokenSingleton {
    private static BrokenSingleton instance;

    public static BrokenSingleton getInstance() {
        if (instance == null) {
            // Two threads can BOTH see null here!
            // → create TWO instances!
            instance = new BrokenSingleton();
        }
        return instance;
    }
}
// Race window: Thread-A checks null → yield
// Thread-B checks null → creates instance
// Thread-A resumes → creates SECOND instance!

Spring Boot: Singleton by Default

@Service   // @Component, @Repository, @Controller
public class UserService {
    // Spring creates EXACTLY ONE instance in ApplicationContext
    // Shared across ALL HTTP requests (200+ threads)

    // ✅ SAFE: stateless service, inject stateless deps
    private final UserRepository repo;

    // ❌ DANGEROUS: instance-level state
    private User currentUser;   // shared by ALL threads!
    private int counter = 0;   // race condition!
}

// Scope options:
@Scope("prototype") // new instance per injection
@Scope("request")   // new instance per HTTP request

⚠️ Most Common Mistake
Storing mutable state in a singleton Spring service. Because it's shared, state leaks between requests. Always make services stateless.

Strategy Pattern

Define a family of algorithms, encapsulate each, and make them interchangeable. Behavioral

// Context: Payment processing with multiple providers

// Strategy interface
public interface PaymentStrategy {
    PaymentResult process(PaymentRequest request);
    boolean supports(String paymentType);
}

// Concrete strategies
@Component
public class StripePaymentStrategy implements PaymentStrategy {
    @Override
    public PaymentResult process(PaymentRequest req) {
        // Stripe API call
        return stripeClient.charge(req.getAmount(), req.getToken());
    }
    @Override
    public boolean supports(String type) { return "STRIPE".equals(type); }
}

@Component
public class PaypalPaymentStrategy implements PaymentStrategy {
    @Override
    public PaymentResult process(PaymentRequest req) {
        return paypalClient.capture(req);
    }
    @Override
    public boolean supports(String type) { return "PAYPAL".equals(type); }
}

// Context — Spring auto-injects ALL PaymentStrategy beans
@Service
public class PaymentService {
    private final List<PaymentStrategy> strategies;

    public PaymentService(List<PaymentStrategy> strategies) {
        this.strategies = strategies;   // injected automatically!
    }

    public PaymentResult pay(PaymentRequest request) {
        return strategies.stream()
            .filter(s -> s.supports(request.getType()))
            .findFirst()
            .orElseThrow(() -> new UnsupportedOperationException(
                "No handler for: " + request.getType()))
            .process(request);
    }
}
// Adding new payment provider = new @Component class!
// Open/Closed principle: open for extension, closed for modification

Observer Pattern

Define a one-to-many dependency so that when one object changes, all dependents are notified. Behavioral

// Event (the observable change)
public class OrderPlacedEvent extends ApplicationEvent {
    private final Order order;

    public OrderPlacedEvent(Object source, Order order) {
        super(source);
        this.order = order;
    }
    public Order getOrder() { return order; }
}

// Publisher (Subject)
@Service
public class OrderService {
    private final ApplicationEventPublisher eventPublisher;

    public Order placeOrder(OrderRequest request) {
        Order order = createOrder(request);
        orderRepo.save(order);

        // Fire event — decoupled from listeners!
        eventPublisher.publishEvent(new OrderPlacedEvent(this, order));

        return order;
    }
}

// Observer 1: Email notification
@Component
public class EmailNotificationListener {

    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) {
        emailService.sendOrderConfirmation(event.getOrder());
    }
}

// Observer 2: Inventory deduction
@Component
public class InventoryListener {

    @EventListener
    @Async  // run in separate thread!
    public void onOrderPlaced(OrderPlacedEvent event) {
        inventoryService.deductStock(event.getOrder().getItems());
    }
}

// Observer 3: Transactional — fires only after commit
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderPlaced(OrderPlacedEvent event) {
    analyticsService.trackPurchase(event.getOrder());
    // Only runs if the DB transaction succeeded
}
💡 @TransactionalEventListener
Always use this for listeners that trigger side effects (emails, 3rd-party APIs). Without it, listeners fire even if the transaction rolls back, sending duplicate emails for failed orders.

Factory Method & Abstract Factory

Define an interface for creating objects, subclasses decide which class to instantiate. Creational

// Factory Method Pattern: Notification system

public interface Notification {
    void send(String message, String recipient);
}

public class EmailNotification implements Notification { /*...*/ }
public class SmsNotification implements Notification { /*...*/ }
public class PushNotification implements Notification { /*...*/ }

// Factory
@Component
public class NotificationFactory {
    private final Map<String, Notification> registry;

    // Spring injects all Notification beans into map!
    // Key = bean name (by default, lowercase class name)
    public NotificationFactory(Map<String, Notification> registry) {
        this.registry = registry;
    }

    public Notification create(String channel) {
        Notification notification = registry.get(channel.toLowerCase() + "Notification");
        if (notification == null) {
            throw new IllegalArgumentException("Unknown channel: " + channel);
        }
        return notification;
    }
}

public class DatabaseConnection {
    private final String host;
    private final int port;
    private final int poolSize;
    private final Duration timeout;

    private DatabaseConnection(Builder b) {
        this.host = b.host; this.port = b.port;
        this.poolSize = b.poolSize; this.timeout = b.timeout;
    }

    public static class Builder {
        private final String host;
        private int port = 5432;
        private int poolSize = 10;
        private Duration timeout = Duration.ofSeconds(30);

        public Builder(String host) { this.host = Objects.requireNonNull(host); }
        public Builder port(int p) { this.port = p; return this; }
        public Builder poolSize(int s) {
            if (s < 1 || s > 100) throw new IllegalArgumentException("poolSize 1-100");
            this.poolSize = s; return this;
        }
        public Builder timeout(Duration t) { this.timeout = t; return this; }
        public DatabaseConnection build() { return new DatabaseConnection(this); }
    }
}

// Usage:

    .port(5432).poolSize(20).timeout(Duration.ofSeconds(10)).build();

Adapter Pattern

Convert the interface of a class into another interface that clients expect. Structural

// Scenario: Integrating legacy payment system with modern interface

// Target interface (what our app expects)
public interface ModernPaymentGateway {
    PaymentResult charge(BigDecimal amount, String currency, String customerId);
    RefundResult refund(String transactionId, BigDecimal amount);
}

// Legacy system we can't modify
public class LegacyPaymentSystem {
    public int processTransaction(double amountCents, String txType, String cid) { /**/ }
    public boolean reverseTransaction(String txId, double amountCents) { /**/ }
}

// Adapter bridges the two
@Component
public class LegacyPaymentAdapter implements ModernPaymentGateway {
    private final LegacyPaymentSystem legacy;

    public LegacyPaymentAdapter(LegacyPaymentSystem legacy) {
        this.legacy = legacy;
    }

    @Override
    public PaymentResult charge(BigDecimal amount, String currency, String customerId) {
        // Adapt: BigDecimal → double cents, add "CHARGE" txType
        double cents = amount.multiply(BigDecimal.valueOf(100)).doubleValue();
        int txId = legacy.processTransaction(cents, "CHARGE", customerId);
        return new PaymentResult(String.valueOf(txId), "SUCCESS");
    }

    @Override
    public RefundResult refund(String transactionId, BigDecimal amount) {
        double cents = amount.multiply(BigDecimal.valueOf(100)).doubleValue();
        boolean ok = legacy.reverseTransaction(transactionId, cents);
        return new RefundResult(ok ? "SUCCESS" : "FAILED");
    }
}

// Service uses only ModernPaymentGateway interface!
@Service
public class CheckoutService {
    private final ModernPaymentGateway gateway; // injected as LegacyPaymentAdapter
}

Decorator Pattern

Attach additional responsibilities to an object dynamically. Flexible alternative to subclassing. Structural

// Base interface
public interface UserService {
    UserDto findById(long id);
    List<UserDto> findAll();
}

// Core implementation
@Service
public class UserServiceImpl implements UserService {
    public UserDto findById(long id) { return repo.findById(id); }
    public List<UserDto> findAll() { return repo.findAll(); }
}

// Decorator 1: Caching
public class CachingUserService implements UserService {
    private final UserService delegate;
    private final Cache<Long, UserDto> cache;

    public CachingUserService(UserService delegate) {
        this.delegate = delegate;
        this.cache = Caffeine.newBuilder().maximumSize(1000)
            .expireAfterWrite(5, TimeUnit.MINUTES).build();
    }

    public UserDto findById(long id) {
        return cache.get(id, k -> delegate.findById(k));  // wraps!
    }
    public List<UserDto> findAll() { return delegate.findAll(); }
}

// Decorator 2: Logging + Metrics
public class LoggingUserService implements UserService {
    private final UserService delegate;

    public UserDto findById(long id) {
        long start = System.currentTimeMillis();
        try {
            UserDto result = delegate.findById(id);
            log.info("findById({}) took {}ms", id, System.currentTimeMillis()-start);
            return result;
        } catch (Exception e) {
            log.error("findById({}) failed", id, e);
            throw e;
        }
    }
    public List<UserDto> findAll() { return delegate.findAll(); }
}

// Compose decorators (order matters!)
@Bean
public UserService userService(UserServiceImpl core) {
    return new LoggingUserService(      // outermost: logs AFTER cache check
        new CachingUserService(core)    // innermost: cache before DB
    );
}

Spring AOP is Decorator via Proxy

// @Transactional, @Cacheable, @PreAuthorize = Decorators!
// Spring creates a PROXY wrapping your bean:

@Service
public class OrderService {

    @Cacheable("orders")          // Decorator: check cache first
    @PreAuthorize("hasRole('USER')") // Decorator: check auth first
    @Transactional                 // Decorator: wrap in transaction
    public Order findById(long id) {
        return orderRepo.findById(id);
    }
    // What actually runs (proxy chain):
    // Auth check → cache check → tx begin → DB → tx commit → cache put → return
}
