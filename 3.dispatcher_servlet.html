6. Custom Interceptor Implementation

@Component
public class RequestTracingInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res,
                              Object handler) {
        String traceId = Optional.ofNullable(req.getHeader("X-Trace-Id"))
            .orElse(UUID.randomUUID().toString().substring(0, 8));

        MDC.put("traceId", traceId);
        res.setHeader("X-Trace-Id", traceId);
        req.setAttribute("startTime", System.currentTimeMillis());

        if (handler instanceof HandlerMethod hm) {
            log.info("[{}] {} {} → {}.{}", traceId,
                req.getMethod(), req.getRequestURI(),
                hm.getBeanType().getSimpleName(),
                hm.getMethod().getName());
        }
        return true;  // false = abort, write your own 4xx
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                 Object handler, Exception ex) {
        long elapsed = System.currentTimeMillis() -
            (Long) req.getAttribute("startTime");
        log.info("[{}] {} {} → {} in {}ms",
            MDC.get("traceId"), req.getMethod(),
            req.getRequestURI(), res.getStatus(), elapsed);
        MDC.clear();  // MUST clear, thread goes back to pool!
    }
}

@Configuration
public class MvcConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(requestTracingInterceptor)
            .addPathPatterns("/api/**")
            .excludePathPatterns("/api/health", "/actuator/**")
            .order(1);
    }
}

Embedded Tomcat Architecture

From socket accept to thread dispatch — Tomcat internals and Spring Boot production tuning

1. Tomcat Internal Architecture

Tomcat Server └── Service ├── Connector (HTTP/1.1 port 8080) │ ├── ProtocolHandler: Http11NioProtocol (non-blocking I/O) │ ├── Endpoint: NioEndpoint │ │ ├── Acceptor thread (1) — accept() blocks for new connections │ │ ├── Poller threads (2) — NIO Selector monitors active sockets │ │ └── Executor (thread pool) — actual request processing │ └── Adapter → CoyoteAdapter → Engine │ └── Engine (Catalina) └── Host (localhost) └── Context (/ your app) └── Wrapper → DispatcherServlet

2. NIO Connection Handling

Phase 1 — Accept (Acceptor thread) ServerSocket.accept() blocks New connection arrives → SocketChannel opened (non-blocking) Register channel with Poller's NIO Selector Phase 2 — Poll (Poller thread) Selector.select() — waits for readable sockets Request bytes arrive → socket becomes readable Poller hands socket to Executor thread pool Phase 3 — Process (Worker thread from pool) HTTP parser reads bytes → Request object CoyoteAdapter.service() → Tomcat pipeline StandardEngineValve → StandardHostValve → StandardContextValve → ApplicationFilterChain → DispatcherServlet KEY INSIGHT: One worker thread is HELD for entire request duration Even during DB query (thread blocks). 200 threads × 200ms avg = ~1000 req/s max

HikariCP — Database Connection Pooling

JDBC lifecycle, pool architecture, starvation, leaks, and tuning for production

1. Why Pooling Is Essential

Without pool — cost of ONE DB call: TCP handshake (3-way) ~1ms TLS negotiation (if SSL) ~5ms PostgreSQL auth (challenge-resp) ~2ms Connection ready ──── Total: ~8ms overhead Actual query execution: ~2ms Overhead = 4× query time! 1000 req/s = 8 seconds of connect time With HikariCP: Pool initialised at startup once getConnection() from pool ~0.05ms Query execution ~2ms returnConnection() to pool ~0.01ms Overhead ≈ 0.06ms → 133× faster

2. JDBC Connection Lifecycle

1
Pool initialization

HikariCP creates minimumIdle physical JDBC connections at startup. Each: TCP connect → auth → idle in pool.

2
Connection request

Thread calls dataSource.getConnection(). HikariCP checks pool for idle connection. Returns instantly if available.

3
Pool empty — wait

If no idle connection, thread waits up to connectionTimeout (default 30s). If still none → SQLTransientConnectionException.

4
Query execution

Connection is borrowed. Thread executes SQL. Connection marked as in-use, not available to others.

5
Connection return

On connection.close() (usually via @Transactional commit/rollback), connection returned to pool, not physically closed.

6
Eviction

Connections idle longer than idleTimeout (default 10m) or older than maxLifetime (default 30m) are closed and replaced.

4. Pool Sizing — The Formula

Connections = threads × (1/parallelism per thread) Practical HikariCP formula (from HikariCP author): pool_size = (core_count × 2) + effective_spindle_count For modern SSD-based PostgreSQL on 4-core server: pool_size = (4 × 2) + 1 = 9 → use 10 For 8-core, network-bound (high latency to DB): pool_size ≈ 8 × 2 = 16-20 is fine Misconception: "more connections = faster" PostgreSQL with 200 connections on 8-core: 192 connections WAIT for CPU Context switching overhead kills throughput Fewer, focused connections outperform many competing ones Rule: max_pool_size * num_app_instances ≤ (db_max_connections × 0.8) Leave 20% for admin queries, monitoring, migrations

5. Pool Starvation — Detection & Fix

❌ Pool starvation scenario
@Transactional
public Order createOrder(req) {
    Order o = orderRepo.save(req);

    // HOLDING DB connection while
    // doing slow external API call!
    emailApi.sendConfirmation(o);  // 2s
    paymentApi.reserve(o);         // 1s

    return o;
    // Total: 3s × 20 threads
    // = all 20 pool connections held!
    // 21st request: SQLTransientConnectionException
}
✅ Release connection before IO
@Transactional
public Order createOrder(req) {
    Order o = orderRepo.save(req);
    return o;
    // TX commits here, conn returned!
}

// Then, outside @Transactional:
public Order processOrder(req) {
    Order o = createOrder(req);  // TX done
    // Connection already returned
    emailApi.sendConfirmation(o);
    paymentApi.reserve(o);
    return o;
}

// @Transactional marks where connection is HELD
// Connection acquired at: first database operation inside @Transactional
// Connection returned at: @Transactional method exits (commit/rollback)

// ❌ Long transaction = long connection hold
@Transactional  // connection held for ENTIRE method duration
public void badExample() {
    var data = repo.findAll();          // connection acquired here

    for (var item : data) process(item); // each call uses same connection
}                                       // connection returned here

// ✅ Load data first, process outside transaction
public void goodExample() {
    List<Data> data;
    try (var tx = txManager.beginTransaction()) {
        data = repo.findAll();
    }  // connection returned immediately after read
    processInMemory(data);  // no connection needed
}

REST Architecture — Properly

Fielding's constraints, HTTP semantics, resource design, caching, HATEOAS — production-grade

1. Roy Fielding's 6 REST Constraints

1. Client-Server

UI concerns separate from data storage. Client doesn't know DB schema. Server doesn't know UI framework. Both evolve independently.

2. Stateless

Every request contains ALL information. No session state on server between requests. State lives in client (JWT, cookies) or resource (DB).

3. Cacheable

Responses must declare themselves cacheable or not via Cache-Control. GET responses cached by CDN/browser saves bandwidth and latency.

4. Uniform Interface

The "REST" constraint. Resource identification in URI. Manipulation via representations. Self-descriptive messages. HATEOAS.

5. Layered System

Client can't tell if connected to origin or proxy. Load balancers, CDNs, API gateways are transparent layers.

6. Code on Demand (optional)

Server can extend client by sending executable code (JavaScript). Makes client lighter. Rarely used in REST APIs.

4. HTTP Caching

// Server-side caching headers
@GetMapping("/products/{id}")
public ResponseEntity<ProductDto> getProduct(@PathVariable Long id) {
    Product product = productService.findById(id);

    // ETag: hash of content, enables conditional requests
    String etag = "\"" + Integer.toHexString(product.hashCode()) + "\"";

    return ResponseEntity.ok()
        .eTag(etag)
        .cacheControl(CacheControl.maxAge(1, TimeUnit.HOURS)
            .mustRevalidate())                   // revalidate after 1 hour
        .lastModified(product.getUpdatedAt())    // If-Modified-Since support
        .body(productMapper.toDto(product));
}

// Client sends: GET /products/1  If-None-Match: "abc123"
// Server: unchanged → 304 Not Modified (no body, saves bandwidth)
// Server: changed  → 200 OK with new ETag

// Cache-Control strategies:
CacheControl.noStore()                     // never cache (user data, security)
CacheControl.noCache()                     // cache but revalidate every request
CacheControl.maxAge(Duration.ofMinutes(5)) // cache for 5 minutes
CacheControl.maxAge(Duration.ofHours(24))
    .cachePublic()                         // CDN can cache (public resource)

5. Content Negotiation

// Client states preference via Accept header:
// Accept: application/json, application/xml;q=0.9, */*;q=0.8
// Spring picks best match from controller's 'produces'

@GetMapping(value = "/report",
    produces = {MediaType.APPLICATION_JSON_VALUE,
                MediaType.APPLICATION_PDF_VALUE,
                "text/csv"})
public ResponseEntity<?> getReport(
        @RequestHeader(HttpHeaders.ACCEPT) String accept) {

    if (accept.contains("application/pdf")) {
        byte[] pdf = reportService.generatePdf();
        return ResponseEntity.ok()
            .contentType(MediaType.APPLICATION_PDF)
            .body(pdf);
    }
    if (accept.contains("text/csv")) {
        String csv = reportService.generateCsv();
        return ResponseEntity.ok()
            .contentType(MediaType.parseMediaType("text/csv"))
            .body(csv);
    }
    return ResponseEntity.ok(reportService.generateDto());  // JSON default
}

7. Pagination Strategies

// Strategy 1: Offset pagination (simple but has issues)
GET /orders?page=3&size=20&sort=createdAt,desc
// SQL: OFFSET 60 LIMIT 20
// Problem: items shift between pages when new records added
// Problem: OFFSET is slow on large tables (scans 60 rows to skip)

// Strategy 2: Cursor pagination (production preferred)
GET /orders?limit=20
// Response: { "data": [...], "nextCursor": "MjAyNC0wMS0xNXwxMjM0NQ==" }
GET /orders?cursor=MjAyNC0wMS0xNXwxMjM0NQ==&limit=20

// Cursor = base64(lastCreatedAt + "|" + lastId)
// SQL: WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20
// Uses composite index: CREATE INDEX idx_orders_created_id ON orders(created_at, id)

@GetMapping("/orders")
public CursorPageResponse<OrderDto> getOrders(
        @RequestParam(required = false) String cursor,
        @RequestParam(defaultValue = "20") int limit) {

    Instant afterTime = null;
    Long afterId = null;

    if (cursor != null) {
        String decoded = new String(Base64.decode(cursor));
        String[] parts = decoded.split("\\|");
        afterTime = Instant.parse(parts[0]);
        afterId = Long.parseLong(parts[1]);
    }

    List<Order> orders = orderRepo.findAfterCursor(afterTime, afterId, limit + 1);
    boolean hasMore = orders.size() > limit;
    if (hasMore) orders.remove(orders.size() - 1);

    String nextCursor = null;
    if (hasMore) {
        Order last = orders.get(orders.size() - 1);
        nextCursor = Base64.encode(last.getCreatedAt() + "|" + last.getId());
    }
    return new CursorPageResponse<>(orders.stream().map(mapper::toDto).toList(), nextCursor, hasMore);
}

3. Critical Bug: REQUIRES_NEW Within Same Bean

❌ BROKEN — self-invocation bypasses proxy
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order o) {
        orderRepo.save(o);
        // this.log() calls REAL object
        // not the proxy!
        // REQUIRES_NEW has NO EFFECT
        this.logAudit(o);
    }

    @Transactional(propagation = REQUIRES_NEW)
    public void logAudit(Order o) {
        // Runs in SAME transaction!
        // If createOrder rolls back
        // audit log rolls back too!
    }
}
✅ Fix: separate Spring bean
@Service
public class OrderService {
    private final AuditService auditService;

    @Transactional
    public void createOrder(Order o) {
        orderRepo.save(o);
        // Calls via proxy!
        auditService.logAudit(o);
        // ↑ REQUIRES_NEW works!
        // Separate connection, separate TX
        // Audit survives even if order rolls back
    }
}

@Service

    @Transactional(propagation = REQUIRES_NEW)

// Custom serializer: BigDecimal → always 2 decimal places
public class MoneySerializer extends JsonSerializer<BigDecimal> {
    @Override
    public void serialize(BigDecimal value, JsonGenerator gen,
                          SerializerProvider provider) throws IOException {
        gen.writeString(value.setScale(2, RoundingMode.HALF_UP).toPlainString());
    }
}

// Custom deserializer: money string → BigDecimal
public class MoneyDeserializer extends JsonDeserializer<BigDecimal> {
    @Override
    public BigDecimal deserialize(JsonParser p, DeserializationContext ctx)
            throws IOException {
        String text = p.getText().replaceAll("[,$€]", "").trim();
        return new BigDecimal(text);
    }
}

}

// Step 1: Define annotation
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = PasswordMatchValidator.class)
public @interface PasswordMatch {
    String message() default "Passwords do not match";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// Step 2: Validator
public class PasswordMatchValidator
        implements ConstraintValidator<PasswordMatch, RegisterRequest> {
    @Override
    public boolean isValid(RegisterRequest req, ConstraintValidatorContext ctx) {
        if (req.getPassword() == null) return true;  // let @NotNull handle null
        if (!req.getPassword().equals(req.getConfirmPassword())) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate("Passwords do not match")
               .addPropertyNode("confirmPassword")  // attach to specific field
               .addConstraintViolation();
            return false;
        }
        return true;
    }
}

// Step 3: Annotate the DTO class
@PasswordMatch

    @NotBlank @Email private String email;
    @NotBlank @Size(min=8) private String password;

@RestControllerAdvice
public class ValidationExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ValidationErrorResponse handleValidation(MethodArgumentNotValidException ex) {
        Map<String, List<String>> errors = new LinkedHashMap<>();

        ex.getBindingResult().getFieldErrors().forEach(fe ->

            errors.computeIfAbsent("_global", k -> new ArrayList<>())
                  .add(ge.getDefaultMessage()));

        return new ValidationErrorResponse(
            "VALIDATION_FAILED",
            "Request validation failed",
            errors,
            Instant.now()
        );
    }
}

2. @Async — Configuration & Pitfalls

// Configuration (ALWAYS define custom executor for @Async)
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Override
    public Executor getAsyncExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(20);
        executor.setQueueCapacity(1000);
        executor.setThreadNamePrefix("Async-");
        executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy()); // backpressure
        executor.setTaskDecorator(task -> {             // context propagation!
            RequestAttributes attrs = RequestContextHolder.currentRequestAttributes();
            Map<String, String> mdc = MDC.getCopyOfContextMap();
            return () -> {
                RequestContextHolder.setRequestAttributes(attrs);
                MDC.setContextMap(mdc != null ? mdc : Collections.emptyMap());
                try { task.run(); }
                finally {
                    RequestContextHolder.resetRequestAttributes();
                    MDC.clear();
                }
            };
        });
        executor.initialize();
        return executor;
    }

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) ->
            log.error("Async exception in {}: {}", method.getName(), ex.getMessage(), ex);
    }
}

4. CompletableFuture — Full Operator Reference

// Async chain: user data + orders + recommendations in parallel
CompletableFuture<User> userFuture =
    CompletableFuture.supplyAsync(() -> userRepo.findById(userId), ioExecutor);

CompletableFuture<List<Order>> ordersFuture =
    CompletableFuture.supplyAsync(() -> orderRepo.findByUser(userId), ioExecutor);

CompletableFuture<List<Product>> recsFuture =
    CompletableFuture.supplyAsync(() -> mlService.recommend(userId), ioExecutor);

// Wait for all three:
CompletableFuture<DashboardDto> dashboard =
    CompletableFuture.allOf(userFuture, ordersFuture, recsFuture)
        .thenApply(v -> DashboardDto.of(
            userFuture.join(),      // join() is safe here (already done)
            ordersFuture.join(),
            recsFuture.join()
        ));

// Timeout + fallback:
DashboardDto result = dashboard
    .orTimeout(5, TimeUnit.SECONDS)     // Java 9+ throws TimeoutException after 5s
    .exceptionally(ex -> DashboardDto.minimal(userId))  // fallback
    .join();

// Operators quick ref:
// .thenApply(fn)         sync transform of result (T → U)
// .thenCompose(fn)       async flatMap (T → CF<U>)
// .thenCombine(cf, fn)   combine two CF results
// .thenAccept(fn)        consume result, return void CF
// .thenRun(fn)           run after completion, no result
// .exceptionally(fn)     handle exception, return fallback
// .handle(fn)            always runs (result or exception)
// .whenComplete(fn)      always runs, can't transform
// .allOf(cf1,cf2,...)    wait for all CFs to complete
// .anyOf(cf1,cf2,...)    wait for first CF to complete

6. Thread Pool Sizing Decision Tree

Is the work CPU-bound or I/O-bound? │ ├─ CPU-bound (hashing, image processing, ML inference) │ pool_size = CPU_cores (+ 1 for GC) │ Usually: 4-8 threads on modern servers │ Use: Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors()) │ ├─ I/O-bound (DB queries, HTTP calls, file I/O) │ pool_size = threads_needed_for_target_throughput │ formula: target_rps × avg_latency_s = concurrent_threads │ Example: 100 req/s × 0.2s avg = 20 threads minimum │ Use: ThreadPoolTaskExecutor with core=20, max=100, queue=500 │ └─ Mixed I/O + CPU (most web apps) Use virtual threads (Java 21): per-task threads, JVM manages Falls back naturally for both patterns No tuning needed for most applications

Failure Scenarios & Diagnosis

// Symptom: SQLTransientConnectionException: Unable to acquire connection within 30000ms

// Diagnosis:
// 1. Check pool metrics:
curl http://localhost:8080/actuator/metrics/hikaricp.connections.pending
// → count > 0 means threads waiting for connections

// 2. Check active connections:
curl http://localhost:8080/actuator/metrics/hikaricp.connections.active
// → equals maximumPoolSize = all connections in use

// 3. Thread dump — look for where connections are held:
curl http://localhost:8080/actuator/threaddump | jq '.threads[].stackTrace'

// Common root causes:
// a) @Transactional method doing slow HTTP call while holding connection
// b) DB server slow → queries taking 10x longer → connections held longer
// c) maximumPoolSize too small for traffic

// Fix a): move external calls outside @Transactional
// Fix b): check DB query plans, add indexes
// Fix c): increase pool size (but not beyond db max_connections)
// Symptom: Application hangs under load, all threads in WAITING state
// Thread dump shows: "exec-1..200" all waiting in HikariPool

// Root cause: transaction holding connection calls another transactional service
// that needs a connection from the SAME pool → circular wait

@Transactional
public void processOrder(Long id) {
    Order o = orderRepo.findById(id);  // connection 1 acquired
    // Calls external service which creates its own @Transactional
    // but it needs connection 2, which might not be available!
    externalService.notify(id);  // this also does DB work
}

// Fix: ensure notify() uses REQUIRES_NEW on different pool
// Or: use async event instead of synchronous call
applicationEventPublisher.publishEvent(new OrderProcessedEvent(id));
// @EventListener @Async runs after TX commits, on different thread
// Symptom: OutOfMemoryError: Java heap space
// Heap dump: large List<Order> objects

// Root cause: loading entire table into memory
// ❌ orderRepo.findAll() with 10M rows = 10M objects in heap

// Fix 1: Pageable
Page<Order> page = orderRepo.findAll(PageRequest.of(0, 1000));

// Fix 2: Stream (Hibernate ScrollableResults)
@Transactional(readOnly = true)
public void exportOrders(OutputStream out) {
    try (Stream<Order> stream = orderRepo.streamAll()) {
        stream.forEach(o -> writeToStream(out, o));
        // processed one-by-one, constant memory
    }
}

// Fix 3: JVM heap settings
// -Xmx should be 70% of container memory
// -XX:+UseG1GC with -XX:MaxGCPauseMillis=200
// -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/
// Symptom: requests hanging, thread dump shows BLOCKED threads
// DB log: "deadlock detected" + rollback

// Root cause: two transactions lock rows in different orders
// TX1: locks order 1 then tries to lock order 2
// TX2: locks order 2 then tries to lock order 1

// Fix 1: consistent lock ordering
// Always fetch/lock in ascending ID order:
List<Long> ids = Arrays.asList(id1, id2);
Collections.sort(ids);
// Then lock in order: ids.forEach(id -> repo.findByIdForUpdate(id));

// Fix 2: optimistic locking (no DB locks)
@Entity
public class Order {
    @Version
    private int version;  // Hibernate adds WHERE version=? to UPDATE
}
// OptimisticLockException on conflict → retry at application layer

// Fix 3: reduce transaction scope
// Shorter transactions = shorter lock holds = less deadlock chance
// Symptom: p50=50ms, p95=200ms, p99=2000ms
// 1% of requests are 40× slower — what's happening?

// Investigation tools:

// 1. Slow query log (PostgreSQL)
//    log_min_duration_statement = 100  ← log queries > 100ms
//    → Check with EXPLAIN ANALYZE for missing indexes

// 2. Micrometer histograms for method timing:
@Timed(value = "order.service.create", percentiles = {0.5, 0.95, 0.99})
public Order createOrder(OrderRequest req) { ... }

// 3. Distributed trace (Micrometer Tracing + Zipkin)
//    spring-boot-starter-actuator
//    micrometer-tracing-bridge-brave
//    → Zipkin shows each step's duration
//    → Find: "HikariCP wait: 1800ms" = pool exhaustion spike

// 4. GC pause correlation
//    Add: -Xlog:gc*:file=gc.log:time
//    GC pause every 30s coincides with p99 spike?
//    → Switch to ZGC: -XX:+UseZGC  (<1ms pauses)
