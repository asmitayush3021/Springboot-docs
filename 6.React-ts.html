TSTypeScript Foundations for React

Closures, the event loop, promises, destructuring, modules — the same JS internals, now with a type layer that eliminates entire bug classes

Why TypeScript-first
Everything you knew about JS still runs — TypeScript compiles away to plain JS. What changes is when bugs are caught. A stale-closure bug, a null property access, a mismatched action shape — in JS these surface at runtime, often in production. In TS the compiler either rejects the code before it ships or forces you to prove you've handled the edge case (narrowing). That shift — runtime bug → compile-time error — is the entire reason product companies standardized on TS for React codebases.

1. Closures — Now With Captured Types

// The closure mechanics are identical to JS. TypeScript's job is to infer
// and lock the TYPE of the captured variable, so misuse is caught early.
interface Counter {
  increment: () => void;
  decrement: () => void;
  getCount: () => number;
}

function makeCounter(): Counter {
  let count: number = 0;                 // inferred as number; TS locks the type forever
  return {
    increment: () => { count++; },
    decrement: () => { count--; },
    getCount: () => count,
  };
}
const counter = makeCounter();
counter.increment();
// counter.increment("2")  ❌ compile error: expects 0 arguments
// counter.getCount() + "1" would still work (TS allows string coercion on +),
// but counter.nonexistentMethod() is caught immediately — the interface is the contract.
What actually changed here
In plain JS, makeCounter() returns a bag of functions and nothing stops a caller from doing counter.increment("oops") or calling a typo'd method that silently returns undefined. The Counter interface is a compile-time contract: any consumer of this closure gets autocomplete and a hard error on misuse — no unit test required to catch it.

Stale Closures — TypeScript Doesn't Prevent the Bug, But It Documents the Shape

// Stale closures are a JS runtime/timing issue — types alone can't fix logic bugs.
// But typing the interval handle and the callback signature prevents a DIFFERENT
// common bug: passing the wrong callback shape into setInterval.
function buggyTimer(): void {
  let count: number = 0;
  const id: ReturnType<typeof setInterval> = setInterval(() => {
    count++;
    console.log(count); // captures initial count=0 → same stale-closure trap as JS
  }, 1000);
}
// ReturnType matters in isomorphic code: Node's setInterval
// returns a Timeout object, the browser's returns a number. Hardcoding `number`
// here would break under Node — a bug TS surfaces immediately if you mistype it.

3. Promises & async/await With Typed Contracts

// A DTO (Data Transfer Object) type describing exactly what the server sends back.
interface User {
  id: string;
  name: string;
  email: string;
}

const fetchUser = (id: string): Promise<User> =>
  fetch(`/api/users/${id}`)
    .then((res: Response) => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json() as Promise<User>;   // `as` here is a TRUST boundary, not proof
    });

async function loadDashboard(userId: string): Promise<{ user: User; orders: Order[]; profile: Profile }> {
  try {
    const user: User = await fetchUser(userId);

    // Promise.all is typed as a TUPLE, not a generic array — each slot keeps its own type
    const [orders, profile]: [Order[], Profile] = await Promise.all([
      fetchOrders(userId),
      fetchProfile(userId),
    ]);

    return { user, orders, profile };
  } catch (err: unknown) {           // TS 4.4+: catch bindings default to `unknown`, not `any`
    if (err instanceof Error) console.error("Dashboard load failed:", err.message);
    throw err;
  }
}
The `as` keyword is not a runtime check
res.json() as Promise<User> tells the compiler "trust me" — it performs zero runtime validation. If the API actually returns { id: 5, fullName: "x" }, TS won't catch it; your app will silently work with `undefined` fields until something breaks downstream. For real safety at the network boundary, parse with a runtime validator (Zod, seen in the Forms and API chapters) and let z.infer<typeof schema> generate the type — that way "the type" and "the actual validation" can never drift apart. 
// Promise.allSettled — typed as a discriminated union per result!
const results: PromiseSettledResult<User>[] = await Promise.allSettled([
  fetchUser("1"),
  fetchUser("2"),
]);
results.forEach((r: PromiseSettledResult<User>) => {
  // r.status narrows the union: inside this branch, TS KNOWS r.value exists
  if (r.status === "fulfilled") console.log(r.value.name);  // r.value: User
  else console.error(r.reason);                          // r.reason: any
});
Discriminated union, your first one
PromiseSettledResult<T> is {status:"fulfilled", value:T} | {status:"rejected", reason:any}. The status field is the "discriminant" — once you check it with ===, TypeScript narrows the whole object inside that branch. This exact pattern (a literal "kind"/"status"/"type" field distinguishing shapes) is how you'll type Redux actions, form states, and API responses later in this handbook.

interface Address { city: string; zip: string; }

  const { name: userName = "Guest", age, address: { city } = { city: "", zip: "" } } = user;

// Spread with Partial — the standard shape for "patch" updates
function updateUser(user: UserRecord, patch: Partial<UserRecord>): UserRecord {
  return { ...user, ...patch };  // Partial = every key optional; can't accidentally add unknown keys

// Optional chaining + nullish coalescing — TS NARROWS through both
function resolveCity(user: UserRecord): string {
  return user.address?.city ?? "Unknown";  // return type is `string`, never `string | undefined`
}
Bug class eliminated
In JS, updateUser(user, { fullName: "x" }) silently creates a stray fullName field nobody reads — a classic "typo'd prop, no error, just missing data" bug. With Partial<UserRecord> as the patch type, that same call is a compile error: fullName does not exist on type UserRecord.

7. Generic Functions — Reusable, Type-Safe by Construction

// Without generics, a reusable "first item" helper loses all type information:
function firstBad(arr: any[]): any { return arr[0]; }   // ❌ caller gets `any` back — no safety at all

// With a generic , the function stays fully reusable AND fully typed:
function first<T>(arr: T[]): T | undefined { return arr[0]; }
const n = first([1, 2, 3]);        // n: number | undefined
const u = first<User>(users);       // u: User | undefined — explicit when inference can't reach far enough

// groupBy: a generic utility keyed by a mapped function — this exact shape
// reappears when normalizing lists into Record for Redux/Zustand
function groupBy<T, K extends string | number>(items: T[], keyFn: (item: T) => K): Record<K, T[]> {
  return items.reduce((acc, item) => {
    const key = keyFn(item);
    (acc[key] ??= []).push(item);
    return acc;
  }, {} as Record<K, T[]>);
}
const byStatus = groupBy(orders, (o) => o.status); // byStatus: Record — keyFn's return type IS K

    2. useEffect — Typed Cleanup and AbortController Generics

    function UserProfile({ userId }: { userId: string }): JSX.Element {
  const [user, setUser] = useState<User | null>(null);

  useEffect((): (() => void) => {
    const controller = new AbortController();

    const loadUser = async (): Promise<void> => {
      try {
        const res: Response = await fetch(`/api/users/${userId}`, { signal: controller.signal });
        const data: User = await res.json();
        setUser(data);
      } catch (e: unknown) {
        if (e instanceof DOMException && e.name === "AbortError") return;  // expected on cleanup
        console.error(e);
      }
    };
    loadUser();

    return () => controller.abort();   // useEffect's return type MUST be `void | (() => void)` — TS enforces this shape
  }, [userId]);

  return <div>{user?.name}</div>;
}
    Why the cleanup function's type matters
    useEffect's signature is (effect: () => (void | (() => void)), deps?) => void. If you accidentally write useEffect(async () => {...}, []), TS immediately flags it — an async function returns Promise<void>, which doesn't match the required cleanup shape. This catches the extremely common "I made my effect callback async" mistake (which silently breaks cleanup and produces a React warning at runtime in plain JS) at compile time instead.

    3. Stale Closures — The Bug Types Can't Fix, Explained Precisely

    ❌ Stale closure — TS types don't prevent this, they just narrate it
    function Timer(): JSX.Element {
  const [count, setCount] = useState<number>(0);

  useEffect((): (() => void) => {
    const id: ReturnType<typeof setInterval> = setInterval(() => {
      // `count` here has TYPE `number`, correctly — but its VALUE is frozen
      // at 0 forever. Types describe shape, not the lifetime of a closure.
      console.log(count);
      setCount(count + 1);  // always (0 + 1) = 1
    }, 1000);
    return () => clearInterval(id);
  }, []);
  return <div>{count}</div>;
}
    ✅ Functional update — the fix is the same as JS, typed for clarity
    function Timer(): JSX.Element {
  const [count, setCount] = useState<number>(0);

  useEffect((): (() => void) => {
    const id: ReturnType<typeof setInterval> = setInterval(() => {
      // setCount's functional-update overload types `prev` from the
      // state's OWN generic — always the current value, never stale.
      setCount((prev: number) => prev + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []);
  return <div>{count}</div>;
}
    Interview framing
    This is one of the most common frontend interview questions: "Does TypeScript prevent stale closures?" No — it's a runtime/timing problem, not a type problem. What TypeScript does give you here is the correctly-typed ReturnType<typeof setInterval> handle (portable between browser and Node), and it forces the cleanup function to actually exist and match the required signature.

    5. Custom Hooks — Generics Make Them Reusable Across Domains

    // useLocalStorage: without the generic, this hook could only ever store one
// fixed shape. With , the SAME implementation safely stores strings, User
// objects, arrays — the caller's usage site determines T, nothing is duplicated.
function useLocalStorage<T>(key: string, defaultValue: T): [T, (value: T | ((prev: T) => T)) => void] {
  const [value, setValue] = useState<T>(() => {
    try {
      const stored: string | null = localStorage.getItem(key);
      return stored ? (JSON.parse(stored) as T) : defaultValue;
    } catch { return defaultValue; }
  });

  const setStored = useCallback((next: T | ((prev: T) => T)): void => {
    setValue((prev: T) => {
      const resolved: T = typeof next === "function" ? (next as (p: T) => T)(prev) : next;
      localStorage.setItem(key, JSON.stringify(resolved));
      return resolved;
    });
  }, [key]);

  return [value, setStored];
}
// Usage — T is inferred from the default value, zero annotation needed by callers:
const [theme, setTheme] = useLocalStorage<"light" | "dark">("theme", "light");
const [draft, setDraft] = useLocalStorage<FormState>("draft", { name: "", email: "" });

// useDebounce: same generic pattern, works for search strings, filter objects, anything
function useDebounce<T>(value: T, delay: number = 300): T {
  const [debounced, setDebounced] = useState<T>(value);
  useEffect((): (() => void) => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return debounced;
}
const [search, setSearch] = useState<string>("");
const debouncedSearch: string = useDebounce<string>(search, 400);
    Why generics beat `any` in custom hooks
    A non-generic useLocalStorage(key: string, defaultValue: any) compiles, but every consumer loses type safety the moment they read the value back — you'd need to re-cast at every call site. The generic version pushes the type parameter to the call site, so theme is correctly "light" | "dark" and draft is correctly FormState, with the hook's internals written exactly once.

// Mutation variables and payload are BOTH typed — a mismatched call site,
// e.g. updateStatus({ orderId: id, status }) instead of { id, status },
// is a compile error rather than a silent 400 from the backend.
interface UpdateStatusVars { id: string; status: OrderStatus; }

export function useUpdateOrderStatus() {
  const queryClient = useQueryClient();

  return useMutation<OrderDto, ApiError, UpdateStatusVars, { snapshot?: OrderDto[] }>({
    mutationFn: ({ id, status }) => orderApi.updateStatus(id, status),

    onMutate: async ({ id, status }): Promise<{ snapshot?: OrderDto[] }> => {
      await queryClient.cancelQueries({ queryKey: ["orders"] });
      const snapshot = queryClient.getQueryData<OrderDto[]>(["orders"]);
      queryClient.setQueryData<OrderDto[]>(["orders"], (old) =>
        old?.map((o) => (o.id === id ? { ...o, status } : o))
      );
      return { snapshot };    // the 4th generic types EXACTLY this rollback context — no `any`
    },
    onError: (_err, _vars, ctx) => {
      queryClient.setQueryData<OrderDto[]>(["orders"], ctx?.snapshot);
    },
    onSettled: () => { queryClient.invalidateQueries({ queryKey: ["orders"] }); },
  });
}
    Why the 4th generic on useMutation matters
    useMutation<TData, TError, TVariables, TContext>'s 4th slot types whatever you return from onMutate — which is exactly what onError and onSettled receive back as context. Skipping it means ctx is implicitly unknown, and ctx?.snapshot becomes a type error you'd otherwise "fix" with an unsafe cast.

    2. useReducer — Discriminated Union Actions (the Textbook TS Pattern)

    // Untyped/loosely-typed reducers let you dispatch { type: "incrment", payload: 1 }
// (typo) and the switch's default case silently swallows it. A discriminated
// union of actions turns "unknown action" into a compile-time impossibility.
interface CartState { items: CartItem[]; total: number; }

type CartAction =
  | { type: "ADD_ITEM"; payload: CartItem }
  | { type: "REMOVE_ITEM"; payload: { id: string } }
  | { type: "CLEAR" };                       // note: no `payload` key at all — and TS enforces that too

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "ADD_ITEM":
      return { items: [...state.items, action.payload], total: state.total + action.payload.price };
    case "REMOVE_ITEM": {
      const removed = state.items.find((i) => i.id === action.payload.id);
      return {
        items: state.items.filter((i) => i.id !== action.payload.id),
        total: state.total - (removed?.price ?? 0),
      };
    }
    case "CLEAR":
      return { items: [], total: 0 };
    // no `default` needed — TypeScript's exhaustiveness check (below) covers it
  }
}
const [state, dispatch] = useReducer(cartReducer, { items: [], total: 0 });
dispatch({ type: "ADD_ITEM", payload: item });
// dispatch({ type: "ADD_ITEM" })              ❌ missing `payload`
// dispatch({ type: "CLEAR", payload: {} })     ❌ `payload` not allowed on CLEAR
    Exhaustiveness checking — catching a missed case at compile time
    Add a fourth action variant later (say APPLY_COUPON) and forget to handle it in the switch — assign the function's return type explicitly and TS will flag the missing branch as "not all code paths return a value." For a hard guarantee, add default: { const _exhaustive: never = action; throw new Error(...); } — if any action variant isn't handled, action won't be assignable to never, and the build fails immediately instead of silently no-op'ing on the unhandled action in production.

    1. Typed Token Service — a Typed JWT Payload Contract

    // NEVER store tokens in localStorage in real terms (XSS risk for refresh tokens) —
// TS doesn't change that security tradeoff. What it CAN do is stop you from
// reading a JWT claim that doesn't exist, or misspelling `exp` as `expiry`.
interface JwtPayload { sub: string; email: string; roles: Role[]; exp: number; }
interface Tokens { accessToken: string; refreshToken?: string; }

const REFRESH_KEY = "app_refresh_token";
let inMemoryToken: string | null = null;

// A small generic helper: decode makes EVERY future JWT claim shape reusable,
// instead of writing base64-decode-and-cast logic in three different places.
function decodeJwt<T>(token: string): T | null {
  try {
    const payload: string = token.split(".")[1];
    return JSON.parse(atob(payload)) as T;
  } catch { return null; }
}

export const tokenService = {
  getAccessToken: (): string | null => inMemoryToken,
  getRefreshToken: (): string | null => localStorage.getItem(REFRESH_KEY),

  setTokens: ({ accessToken, refreshToken }: Tokens): void => {
    inMemoryToken = accessToken;
    if (refreshToken) localStorage.setItem(REFRESH_KEY, refreshToken);
  },

  getUser: (): User | null => {
    const token = inMemoryToken;
    if (!token) return null;
    const payload = decodeJwt<JwtPayload>(token);
    if (!payload || payload.exp * 1000 < Date.now()) return null;   // expired — TS forces the null path to be handled by callers
    return { id: payload.sub, email: payload.email, roles: payload.roles };
  },

  isTokenExpiringSoon: (): boolean => {
    if (!inMemoryToken) return true;
    const payload = decodeJwt<JwtPayload>(inMemoryToken);
    if (!payload) return true;
    return (payload.exp * 1000 - Date.now()) < 60 * 1000;
  },

  clear: (): void => { inMemoryToken = null; localStorage.removeItem(REFRESH_KEY); },
};
    TypeScript does not validate the JWT signature
    decodeJwt<JwtPayload> only shapes what's already inside the token — it performs zero cryptographic verification. A malicious or tampered token still decodes "successfully" into a well-typed object. Signature verification belongs on the server; the type here exists purely to make the client's own reads of a (server-trusted) token safe and typo-proof.

    2. Silent Refresh — Typed Timer Handle

    function useTokenRefresh(): void {
  const { logout } = useAuth();

  useEffect((): (() => void) | void => {
    const scheduleRefresh = (): (() => void) | void => {
      const token = tokenService.getAccessToken();
      if (!token) return;

      const payload = decodeJwt<JwtPayload>(token);
      if (!payload) { logout(); return; }

      const msUntilExpiry: number = payload.exp * 1000 - Date.now();
      const refreshIn: number = msUntilExpiry - 60 * 1000;
      if (refreshIn <= 0) { logout(); return; }

      const timer: ReturnType<typeof setTimeout> = setTimeout(async () => {
        try {
          const refreshToken = tokenService.getRefreshToken();
          if (!refreshToken) { logout(); return; }
          const { accessToken }: { accessToken: string } = await authApi.refreshToken(refreshToken);
          tokenService.setTokens({ accessToken });
          scheduleRefresh();
        } catch { logout(); }
      }, refreshIn);
      return () => clearTimeout(timer);
    };
    return scheduleRefresh();
  }, [logout]);
}

    TSTypeScript Under the Hood

    The compiler internals — treat this like learning the JVM after learning Java. Nothing here is React-specific; everything here explains why the React chapters behave the way they do.

    The TypeScript Compiler Pipeline (tsc / the language service behind your editor) source.tsx │ ▼ 1. Scanner (Lexer) — chars → tokens (`const`, `x`, `:`, `number`, `=`, `5`, `;`) │ ▼ 2. Parser — tokens → AST (Abstract Syntax Tree), with error recovery │ ▼ 3. Binder — walks the AST once, creates Symbols, builds scopes or a "symbol table" │ ▼ 4. Checker — the actual "TypeScript" part: type inference, structural comparison, │ control flow analysis, narrowing — LAZY, on-demand, memoized per node ▼ 5. Transformer — strips types, downlevels syntax (optional chaining → ternaries for old targets), │ compiles JSX → React.createElement / jsx-runtime calls ▼ 6. Emitter — writes out .js, .d.ts (if declaration:true), and .js.map Key fact: steps 1-4 never touch runtime. Only step 6 produces anything that ships to the browser.

    1. Parsing — From Characters to a Tree the Checker Can Reason About

    What problem does it solve?
    JavaScript/TSX text is just a string. Before anything can be "type-checked," it must become a structured tree: a VariableStatement node containing an Identifier and an initializer expression, etc. The parser also has to recover from errors gracefully — your editor still gives you IntelliSense on a file with a syntax error three lines up, because the parser inserts "missing node" placeholders instead of aborting.

    How it's implemented: a hand-written recursive-descent parser (not generated from a grammar file) walks tokens and builds a strongly-typed AST — every node kind (SyntaxKind.FunctionDeclaration, SyntaxKind.JsxElement, etc.) is a discriminated union tag, which is itself a nice bit of dogfooding: the compiler's own source uses the same "kind" discriminant pattern taught in the Architecture chapter.

    How the compiler reasons: the AST is a pure syntax tree — it knows nothing about types yet. let x = 5 and let x: Banana = 5 produce structurally similar nodes; type information is attached later by the checker, not the parser.

    Where it shows up in React projects: JSX parsing specifically — <div className="x">{children}</div> parses into a JsxElement node tree that mirrors the DOM structure. This is why a single unclosed tag anywhere in a large component can make your whole editor's syntax highlighting go dark past that point — the parser's error-recovery has a strong local effect but a real cascading one.

    Interview angle
    "Does TypeScript use a parser generator like ANTLR/yacc?" No — hand-written recursive descent, for speed and precise error recovery, which a generated parser makes harder to customize.

    2. Type Checking — Lazy, On-Demand, Structural

    Problem: checking every possible type relationship eagerly for a large codebase would be extremely slow, and most of a program's types are never actually compared against most other types.

    Implementation: the checker computes types lazily — it only computes the type of a node when something asks for it (hovering in your editor, or another node needing it to check a relationship), and memoizes the result. Type relationships (is A assignable to B?) are computed via structural comparison: recursively compare member sets, not names.

    Where in React: every time you see a red squiggle under a JSX prop, you're seeing the checker compare the structural shape of the object literal you passed against the component's declared Props type — member by member.

    3. Control Flow Analysis (CFA) — How Narrowing Actually Works

    CFA walks a per-function "control flow graph," not just the AST function f(x: string | number) { if (typeof x === "string") { // CFA node: "reachable only when typeof x === string" → x narrowed to string HERE x.toUpperCase(); } else { // CFA node: the negation of the above → x narrowed to number HERE x.toFixed(2); } } The narrowed type is NOT a property of the variable `x` globally — it's a property of the SPECIFIC NODE in the control flow graph where `x` is referenced. This is why: if (typeof x === "string") { x.toUpperCase(); } x.toUpperCase(); ❌ error — outside the `if`, back to string | number

    How the compiler reasons: for every reference to a variable, the checker walks backward through the control-flow graph collecting narrowing "facts" — typeof checks, instanceof, discriminant property comparisons (action.type === "ADD_ITEM"), truthiness checks, in checks, and user-defined type guards (function isUser(x): x is User) — and intersects them.

    Where in React: every discriminated-union render branch in this handbook (DashboardState, CartAction) relies entirely on CFA. It's also why extracting a condition into a separate boolean variable can sometimes break narrowing — the compiler's CFA can't always "see through" an intermediate variable the way it sees through an inline check (this is a very common gotcha and interview trap).

    Common misconception
    "TypeScript remembers that `user` was checked for null earlier in the function, forever." False — narrowing is invalidated the moment a variable could have been reassigned by an intervening function call (because that callback could theoretically be typed to accept a wider type and someone could have mutated a closed-over variable) unless it's a const or effectively-const local. This is why narrowing works reliably on const bindings and can silently "reset" on let across async boundaries.

    4. Structural Typing (and Why TypeScript Chose It)

    Nominal typing (Java/C#/Kotlin)
    // Two types with IDENTICAL fields are still
// DIFFERENT types unless one explicitly extends/implements the other.
class Point2D { x: number; y: number; }
class Vector2D { x: number; y: number; }
// A Point2D is NOT assignable to Vector2D
// even though the shapes are identical.
    Structural typing (TypeScript)
    interface Point2D { x: number; y: number; }
interface Vector2D { x: number; y: number; }
const p: Point2D = { x: 1, y: 2 };
const v: Vector2D = p;  // ✅ assignable — SAME SHAPE = SAME TYPE
// "If it walks like a duck and quacks like a duck..."

    Why this design decision exists: JavaScript is already a duck-typed, prototype-based language with no nominal type system at runtime — object literals, JSON responses, and function arguments are matched by shape everywhere in idiomatic JS. A nominal type system bolted onto JS would reject enormous amounts of perfectly valid, already-working JavaScript (e.g. passing a plain object literal where an "interface" is expected), which would have killed adoption. Structural typing is what makes TypeScript feel like "JavaScript with types" rather than "a new language."

    Emulating nominal typing when you actually need it (branded types)
    type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
// Without branding, orderApi.getOrder(userId) compiles fine — both are `string`.
// With branding, passing a UserId where OrderId is expected is a compile error —
// the "__brand" field never exists at runtime; it's a pure compile-time tag.

    5. Type Erasure — Why TypeScript "Disappears"

    Problem it solves: browsers and Node don't understand interface, : number, or <T>. For TypeScript to be deployable anywhere JS already runs — with zero new runtime, zero performance cost, zero new engine — every type-level construct must be removable without changing program behavior.

    How it's implemented: the Transformer/Emitter stage deletes all type annotations, interfaces, type aliases, and generic parameters, keeping only the runtime-meaningful JS. Nothing about types is retained in the output .js file (except optionally in a sibling .d.ts file, which itself is never loaded by a JS runtime).

    // INPUT (.tsx)
interface User { id: string; name: string; }
function greet<T extends User>(user: T): string { return `Hi ${user.name}`; }

// OUTPUT (.js) — the interface, the generic, ALL type annotations: gone.
function greet(user) { return `Hi ${user.name}`; }
    Direct consequence: no runtime reflection on types
    You cannot write if (value instanceof User) where User is an interface — interfaces don't exist at runtime, so there is nothing to check against. This is precisely why the handbook's API/Forms chapters lean on Zod: z.object({...}) is a real runtime value with a real .parse() method, and z.infer<typeof schema> derives the erased compile-time type FROM that runtime value — bridging the exact gap that erasure creates.
    Interview question
    "Why doesn't TypeScript support real enums with runtime type checks the way `class` does?" — class compiles to a real runtime constructor function (so instanceof works), but interface/type are pure compile-time constructs with zero runtime footprint. Understanding this distinction is one of the fastest ways to sound senior in an interview.

    6. Declaration Files (.d.ts) & Ambient Declarations

    Problem: most of the JavaScript ecosystem (react, lodash, axios internals) is written in plain JS, or ships compiled output with the types stripped. TypeScript still needs to know their shapes to type-check code that imports them.

    Implementation: a .d.ts file contains ONLY type declarations, zero implementation — it's a pure "shape contract" describing what a JS module exports, without providing the executable code. @types/react (DefinitelyTyped) is exactly this: thousands of hand-maintained .d.ts files describing libraries that don't ship their own types.

    // react-router-dom.d.ts (simplified) — no function bodies, just shapes
export declare function useParams<T extends Record<string, string | undefined>>(): T;

// Ambient declarations: describing things that exist GLOBALLY, not via import —
// e.g. telling TS that importing a .svg file returns a component (Vite/webpack magic)

  const content: React.FC<React.SVGProps<SVGSVGElement>>;
  export default content;
}
// declare global augments the GLOBAL scope, e.g. adding a window.__APP_CONFIG__
declare global { interface Window { __APP_CONFIG__: { apiUrl: string }; } }

    Where in React: every time you import logo from "./logo.svg" or import.meta.env.VITE_API_URL works without a "cannot find module" error, an ambient declaration (usually vite-env.d.ts, auto-generated) is making it possible.

    7. Module Resolution

    Problem: import { Button } from "../shared/components/Button" — which actual file does that resolve to? Button.ts? Button.tsx? Button/index.ts? A node_modules package with its own internal resolution rules?

    Implementation: controlled by the moduleResolution tsconfig option — "classic" (legacy), "node10" (mimics old CommonJS require resolution: check exact file, then with extensions, then index, then walk up node_modules), or the modern "bundler"/"node16"/"nodenext" modes which respect a package's package.json "exports" map — critical for correctly resolving dual ESM/CJS packages like modern versions of axios or React itself.

    Interview trap
    "Why does my import resolve fine in the IDE but fail at build time (or vice versa)?" — usually a mismatch between the TypeScript moduleResolution setting and the actual bundler's (Vite/webpack) resolution algorithm; they must agree, because `tsc` and the bundler are two SEPARATE tools reading the same source.

    10. Incremental Compilation & Project References

    Problem: re-checking an entire large monorepo on every keystroke or every CI run doesn't scale.

    Incremental compilation: with "incremental": true, `tsc` writes a .tsbuildinfo file recording per-file dependency and diagnostic info; the next run only re-checks files that changed (or whose dependencies changed), rather than the whole program.

    Project references: "composite": true projects declare explicit dependencies between sub-projects (e.g. a shared-ui package referenced by both a web app and a mobile app) via "references": [{ "path": "../shared-ui" }]. This lets `tsc --build` compile only the sub-projects that changed, in correct dependency order — the same underlying idea as an incremental build graph in Gradle/Maven multi-module builds, which will feel familiar coming from Spring Boot multi-module projects.

    11. Source Maps

    Problem: the browser only ever runs the emitted, type-erased, possibly-downleveled JavaScript — but you want breakpoints and stack traces in your ORIGINAL .tsx source.

    Implementation: the emitter writes a .js.map file encoding a compact mapping from every position in the generated JS back to a line/column in the original TS source (using VLQ-encoded segments — the same source map format shared with Babel/webpack/Vite). Chrome DevTools reads this mapping to let you set breakpoints directly in .tsx even though the browser never executed a byte of it.

    Full-picture recap: what "compiling away" really means
    Parsing → Binding → Checking → CFA/narrowing all happen ONLY inside your editor and at build time. By the time a React app reaches the browser, none of that machinery exists — just plain, erased JavaScript plus an optional map file pointing back to source you'll never actually ship.

    1. `unknown`, Narrowing & Type Guards — The Untrusted-JSON Problem

    Production Type System, step by step: We receive JSON from a Spring Boot endpoint. │ ▼ The compiler cannot trust its shape — a network response is not a TS value. │ ▼ Type it as `unknown` (NOT `any`) — forces every consumer to prove the shape before use. │ ▼ Narrowing — typeof / property checks / a Zod parse reduce `unknown` toward a real type. │ ▼ Type Guards — a reusable, named predicate function centralizes the narrowing logic. │ ▼ Validated DTO — a value the rest of the app can trust and pass around freely. 
    // A hand-rolled type guard — the `x is OrderDto` return annotation is what makes
// this function special: calling it doesn't just return a boolean, it teaches CFA
// to narrow the checked value wherever this function is used as a condition.
function isOrderDto(value: unknown): value is OrderDto {
  return (
    typeof value === "object" && value !== null &&
    "id" in value && "status" in value && "total" in value
  );
}

async function fetchOrder(id: string): Promise<OrderDto> {
  const res = await fetch(`/api/v1/orders/${id}`);
  const raw: unknown = await res.json();       // unknown — NOT any — the compiler forces a check before use
  if (!isOrderDto(raw)) throw new Error("Malformed order response");
  return raw;                                        // raw is narrowed to OrderDto here — safe to return
}
    Why `unknown`, not `any`
    any disables type checking entirely — every property access, every method call on an any compiles, correct or not. unknown is the "top type" that still requires proof: you cannot call .toUpperCase() or read .status on an unknown until you've narrowed it. It's the type-safe way to say "I don't know this shape yet" instead of "give up checking this forever."

    React usage: untyped 3rd-party event payloads, window.postMessage data, error in a catch block (as seen throughout this handbook), and any JSON.parse result. Spring Boot tie-in: literally every controller response body until validated — pairs naturally with the DTO chapter's Zod schemas, where schema.safeParse(raw) IS the type guard, generated for you instead of hand-written.

    Interview follow-up
    "What's the difference between a user-defined type guard and a Zod schema parse?" — a hand-written guard is a compile-time promise you personally verify is correct (TS trusts you completely); a runtime validator like Zod actually walks the data recursively and rejects malformed input — strictly safer for network boundaries, at the cost of a small runtime overhead.

    This "validated shape" is exactly what feeds into generic, reusable code — which is where generics come in next.

    2. Generics & Constraints — The Copy-Pasted-Repository Problem

    Production problem: OrderRepository, UserRepository, ProductRepository each hand-write getById / getAll / create / update / delete — 90% identical code, 5 features, 5x the bugs. │ ▼ solve with a generic base Repository<T, CreateDto> — write CRUD ONCE, parameterized by the entity shape. │ ▼ but T can't be "anything" — it must at minimum have an `id` Constrain T extends { id: string } — the compiler now REQUIRES every entity to carry an id. 
    // Constraint (`T extends { id: string }`) — without it, `entity.id` inside the class
// body would be a compile error, because a fully-generic T could be ANY shape.
interface Identifiable { id: string; }

class Repository<T extends Identifiable, CreateDto> {
  constructor(private basePath: string) {}

  getById = (id: string): Promise<T> =>
    apiClient.get<T>(`${this.basePath}/${id}`).then((r) => r.data);

  getAll = (): Promise<T[]> =>
    apiClient.get<T[]>(this.basePath).then((r) => r.data);

  create = (dto: CreateDto): Promise<T> =>
    apiClient.post<T>(this.basePath, dto).then((r) => r.data);

  update = (id: string, patch: Partial<T>): Promise<T> =>
    apiClient.patch<T>(`${this.basePath}/${id}`, patch).then((r) => r.data);
}

// One class, every entity — each instantiation is fully typed with NO duplicated logic
export const orderRepository = new Repository<OrderDto, CreateOrderDto>("/api/v1/orders");
export const productRepository = new Repository<ProductDto, CreateProductDto>("/api/v1/products");

    Architecture impact: this IS the Repository Pattern from the Spring Boot world, ported to the frontend — the same motivation (uniform data access, swappable implementation) applies on both sides of the stack.

    Interview follow-up
    "Why constrain T instead of leaving it fully generic?" — an unconstrained T gives you zero guarantees inside the generic code; you couldn't even read entity.id for cache-keying without the constraint. Constraints are how you say "generic, but not infinitely generic."

    Generic constraints often need to reference "the keys of a type" directly — which is exactly what keyof is for.

    3. `keyof` & `typeof` — The Stringly-Typed Field Name Problem

    Production problem: register("emial") in a form, or sortBy("statuss") in a table — a typo'd STRING field name compiles fine and fails silently at runtime. │ ▼ keyof OrderDto — a UNION of the literal string keys of a type: "id" | "status" | "total" | "createdAt" │ ▼ Every function accepting a field name now accepts ONLY real keys of that DTO. 
    function sortBy<T>(items: T[], field: keyof T): T[] {
  return [...items].sort((a, b) => (a[field] > b[field] ? 1 : -1));
}
sortBy(orders, "total");     // ✅
// sortBy(orders, "totall")  ❌ compile error — Argument of type '"totall"' is not assignable to keyof OrderDto

// typeof (in TYPE POSITION, not the JS runtime operator!) — derives a TYPE from a VALUE.
// This is the #1 way senior engineers avoid type/implementation drift: define the
// value ONCE, derive the type FROM it, instead of maintaining both by hand.
const initialCartState = { items: [] as CartItem[], total: 0, status: "idle" as const };
type CartState = typeof initialCartState;   // { items: CartItem[]; total: number; status: "idle" }

// keyof typeof — combined, this is how you type an OBJECT used as an enum:
const ORDER_STATUS = { PENDING: "PENDING", PAID: "PAID", SHIPPED: "SHIPPED" } as const;
type OrderStatusKey = keyof typeof ORDER_STATUS;         // "PENDING" | "PAID" | "SHIPPED"

    React usage: register(name: keyof FormValues) in React Hook Form (Chapter 9), Can permission: keyof Permissions in the RBAC chapter, sortable table column keys. Interview follow-up: "What does keyof any return?" — string | number | symbol, the three possible JS object key types.

    Once you have a key, the natural next question is "what's the TYPE at that key" — Indexed Access Types answer that.

    4. Indexed Access Types — The "Type of One Field, Not the Whole DTO" Problem

    // Production problem: a component only needs the TYPE of `OrderDto["status"]`,
// not the whole DTO — duplicating the union manually risks drift if the DTO changes.
type Status = OrderDto["status"];              // "PENDING" | "PAID" | "SHIPPED" | "CANCELLED" — pulled straight from the DTO
type FirstOrderItem = CreateOrderDto["items"][number];  // indexing an array TYPE with `number` gets its element type

// Real usage: typing a single Redux/Zustand selector's return without re-declaring it
const selectOrderStatus = (state: RootState): RootState["orders"]["status"] => state.orders.status;

    This pattern lets a form's field-level error type, a table column's cell type, or a Redux selector's return type track the source-of-truth DTO automatically — rename a field in the DTO and every indexed-access usage either updates silently or breaks loudly at the exact call site that needs fixing.

    5. Mapped Types — The "One DTO, Many Derived Shapes" Problem

    Production problem: a form needs an ERRORS shape that mirrors its VALUES shape, field-for-field, but with every value replaced by `string | undefined`. │ ▼ Mapped type: { [K in keyof T]: string | undefined } — loop over T's keys, transform each value. 
    type FormErrors<T> = { [K in keyof T]?: string };
// FormErrors = { name?: string; email?: string; password?: string; ... }
// Add a field to RegisterForm and FormErrors picks it up automatically — zero duplication.

// This is EXACTLY how the built-in Partial, Required, and Readonly are implemented:
type MyPartial<T> = { [K in keyof T]?: T[K] };     // `?` makes every key optional — this IS lib.es5.d.ts's Partial
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };

// Key remapping (`as`) — building a typed event-handler-prop map from a plain field map
type ChangeHandlers<T> = { [K in keyof T as `on${Capitalize}Change`]: (value: T[K]) => void };
// ChangeHandlers<{ name: string; age: number }> becomes:
// { onNameChange: (value: string) => void; onAgeChange: (value: number) => void }

    Spring Boot tie-in: mapped types are how you'd model a "partial update DTO" or a validation-error-bag that MUST stay structurally in lockstep with a Java record's fields — instead of manually re-typing the shape.

    6. Conditional Types & `infer` — The "Extract What's Inside" Problem

    Production problem: an async thunk's payload type is buried inside a Promise<T> return type of a function you didn't write the signature of by hand — you need T, not Promise<T>. │ ▼ Conditional type: T extends Promise<infer U> ? U : T — "if T matches this shape, CAPTURE the inner part as U" 
    // `infer` INTRODUCES a new type variable inside a conditional type's `extends` clause —
// it's how the compiler "reaches inside" a generic wrapper and names what it finds.
type Unwrap<T> = T extends Promise<infer U> ? U : T;
type OrderResult = Unwrap<ReturnType<typeof orderApi.getOrder>>;  // OrderDto, not Promise
// This IS how the built-in Awaited utility type works internally.

// ReturnType and Parameters — both built with conditional + infer over function types
type MyReturnType<T extends (...args: any[]) => any> = T extends (...args: any[]) => infer R ? R : never;

// Real production usage: extracting the ELEMENT type of whatever an API returns as a page
type ElementOf<T> = T extends (infer E)[] ? E : never;
type OrderItem = ElementOf<OrderPageDto["orders"]>;    // OrderDto
    Interview follow-up
    "How is `ReturnType<T>` actually implemented?" — most engineers say "it's a built-in keyword"; the correct, senior-level answer is "it's a conditional type using `infer` over a function-type extends clause," defined in TypeScript's own lib.es5.d.ts, not compiler magic.

    7. Literal Types & `as const` — The Widening Problem

    Production problem: const status = "PENDING" — by default TS WIDENS this to the general type `string`, not the specific literal "PENDING" — losing precision the instant you need it. │ ▼ as const — freezes the value AND its type to the exact literal, recursively, and marks it readonly. 
    const a = "PENDING";              // type: string  — widened, loses the literal
const b = "PENDING" as const;    // type: "PENDING" — exact literal preserved

// The big production payoff: config objects become a fully-typed, closed set —
// used throughout this handbook for tab configs, route configs, permission lists.
const TABS = ["overview", "orders", "settings"] as const;
type Tab = (typeof TABS)[number];   // "overview" | "orders" | "settings" — indexed access + as const, combined

// Without `as const`, TABS.map(t => ...) gives each `t` the type `string` —
// with it, `t` is the precise union, and an invalid tab name anywhere is caught.

    This is the same mechanism behind cva's VariantProps in the Styling chapter — as const is what lets a plain JS config object drive a fully derived TypeScript union, with zero hand-maintained type declarations.

    9. Variance — Why Function Parameters Are Special

    Production problem: if Dog extends Animal, is a function (d: Dog) => void assignable where (a: Animal) => void is expected, or the reverse? Getting this backward silently breaks type safety for event handler props — a very common source of confusing errors when passing callback props between differently-typed components.

    // Covariant (safe): a function that RETURNS a more specific type can replace
// one returning a more general type — narrower output is always fine to hand back.
type Producer = () => Animal;
const dogProducer: Producer = (): Dog => new Dog();  // ✅ a Dog IS an Animal

// Contravariant (the strict, mathematically correct rule for parameters):
// a function that ACCEPTS a MORE GENERAL type can replace one accepting a more specific type.
type Handler = (d: Dog) => void;
const animalHandler: Handler = (a: Animal): void => {};  // ✅ under strictFunctionTypes: handling ANY Animal safely handles a Dog too
    Interview-level nuance
    Before strictFunctionTypes, TypeScript used "bivariant" checking for method-syntax functions (for pragmatic compatibility with common JS patterns like DOM event handler overrides) — meaning parameter types could unsoundly flow BOTH ways. This is a real, citable gap between TypeScript's type system and formal type theory, and naming it correctly ("bivariant method parameters, contravariant function-type parameters") is a strong signal in interviews at companies that care about type-system rigor.

  | { status: "submitted"; submittedAt: string }
  | { status: "paid"; paidAt: string }
  | { status: "shipped"; trackingId: string }
  | { status: "cancelled"; reason: string };

  | { type: "SUBMIT" } | { type: "PAY" }
  | { type: "SHIP"; trackingId: string } | { type: "CANCEL"; reason: string };

// shipping a "draft" order) can be made IMPOSSIBLE by narrowing on `state.status` first.
function transition(state: OrderMachineState, event: OrderEvent): OrderMachineState {
  if (state.status === "draft" && event.type === "SUBMIT") return { status: "submitted", submittedAt: new Date().toISOString() };
  if (state.status === "submitted" && event.type === "PAY") return { status: "paid", paidAt: new Date().toISOString() };
  if (state.status === "paid" && event.type === "SHIP") return { status: "shipped", trackingId: event.trackingId };
  if (event.type === "CANCEL") return { status: "cancelled", reason: event.reason };
  return state;   // invalid transition for current state → no-op, never a crash
}

    Not a question bank — the reasoning interviewers are actually probing for.

    Q: Why prefer `interface` over `type` (or vice versa)?

    Expected answer: Interfaces support declaration merging (two `interface Foo` declarations combine into one — critical for augmenting third-party/global types, as in the Theme System pattern above) and communicate "this is an object shape meant to be extended/implemented." `type` aliases can express unions, tuples, mapped/conditional types — things `interface` structurally cannot. The idiomatic modern answer: interface for public object/component-prop shapes that might be extended; type for unions, tuples, and anything derived via mapped/conditional types.

    Common incorrect answer: "They're basically the same, just use whichever" — technically almost true for plain object shapes, but ignores declaration merging and the union/mapped-type limitation, which IS the point of the question.

    Follow-up: "Show me an example where interface merging is actually useful." → the declare module "styled-components" { interface DefaultTheme {...} } pattern from the Patterns chapter.

    Trade-off: merging is a double-edged sword — it can also cause SURPRISE type expansion in large codebases if two unrelated files accidentally declare the same interface name.

    Q: Why does TypeScript use structural typing instead of nominal typing?

    Expected answer: JavaScript itself has no nominal type system — object literals and duck-typed function arguments are pervasive. A nominal system would reject huge amounts of valid, idiomatic JS (see Chapter 13, "Structural Typing"). Structural typing is what makes TS a superset of JS in spirit, not just in syntax.

    Common incorrect answer: "Because it's simpler to implement" — implementation ease isn't the driver; ecosystem compatibility is.

    Follow-up: "How would you emulate nominal typing when you genuinely need it?" → branded/tagged types (string & { __brand: "UserId" }).

    Company-level expectation: Microsoft-level interviews (TypeScript is a Microsoft project) may ask you to trace WHY two structurally-identical interfaces are assignable, expecting you to describe recursive member comparison, not just "it just works."

    Q: How does narrowing work internally?

    Expected answer: the checker builds a control-flow graph per function; for every reference to a variable, it walks backward through reachable predecessor nodes, collecting narrowing "facts" from conditions (typeof, instanceof, discriminant equality, truthiness, in, user-defined type guards) and intersects them into the type at that specific point. Narrowing is a property of a NODE in the graph, not a global fact about the variable.

    Common incorrect answer: "TypeScript remembers the check for the rest of the function" — wrong; it's scoped to control-flow-reachable code, and can be invalidated by reassignment or an intervening function call on a `let`.

    Follow-up: "Why can extracting a condition into a separate variable sometimes break narrowing?" → the compiler can't always prove the extracted variable wasn't reassigned between the check and the use; inlining keeps the fact directly attached to the checked expression.

    Q: Why is `any` dangerous?

    Expected answer: `any` isn't just "no type" — it's contagious. It disables checking on every operation performed on it AND on everything it touches (assigning an `any` to a typed variable silently makes future reads through that variable unchecked too). It's the single biggest way type safety silently evaporates in a large codebase without any visible signal.

    Common incorrect answer: "It's just like JavaScript, so it's fine for quick prototyping" — true in isolation, dangerously wrong once `any` leaks into shared/library code other engineers build on top of.

    Follow-up: "What's the practical difference between `any` and `unknown`?" → `unknown` requires narrowing before any operation; `any` allows everything, silently.

    Q: Why does `unknown` exist (if `any` already did the job)?

    Expected answer: `any` predates a real "top type" being available for "I don't know this shape yet, but I still want safety." `unknown` was added specifically to give library authors and API boundaries (JSON parsing, catch clauses) a way to represent "untyped input" WITHOUT disabling the checker — see the "Production Type System" chapter's JSON-narrowing example.

    Follow-up: "Why does TypeScript 4.4+ type catch-clause bindings as `unknown` by default (with `useUnknownInCatchVariables`)?" → because a `throw` can throw literally anything in JS (not just `Error` instances) — treating it as `any` previously let you call `.message` on something that might be a string or a number, silently.

    Q: Why do React hooks lean so heavily on generics?

    Expected answer: hooks are meant to be reusable across many different data shapes (`useState`, `useQuery`, custom hooks like `useLocalStorage<T>`) — without generics, a hook would either need one implementation per shape (duplication) or fall back to `any` (losing safety entirely). Generics let the hook's implementation be written ONCE while every call site keeps full type precision, with the type parameter typically inferred from the initial value or explicit call-site annotation.

    Follow-up: "Why does `useState(null)` need an explicit generic but `useState(0)` doesn't?" → inference from the initial value; `null`'s inferred type is the unusable literal `null`, so you must supply the real union yourself (useState<User | null>(null)).

    Q: How is `keyof` implemented / reasoned about by the compiler?

    Expected answer: `keyof T` produces a union of string/number/symbol literal types corresponding to every known property key of `T`, computed structurally by walking `T`'s member list — it's not a runtime reflection operation (it can't be; `T` is erased), it's purely a compile-time projection over the type's declared shape.

    Follow-up: "What does `keyof any` evaluate to, and why?" → string | number | symbol — the three types JavaScript actually permits as object property keys.

    Q: How does `Partial<T>` actually work?

    Expected answer: it's a mapped type, defined in TypeScript's own standard library as { [P in keyof T]?: T[P] } — loop over every key of `T`, keep the same value type, add the optional modifier. It's not compiler-special-cased syntax; you could write an identical utility yourself (as shown in Chapter 14).

    Follow-up: "Implement `Required<T>` from scratch." → { [P in keyof T]-?: T[P] } — the -? modifier REMOVES optionality, the mirror image of `Partial`'s `?`.

    Q: Why do mapped types exist at all?

    Expected answer: to eliminate hand-duplicating a type's shape every time you need a structurally-related-but-transformed version of it (all-optional, all-readonly, error-bag-per-field, event-handler-per-field) — see the `FormErrors<T>` production example in Chapter 14. Without mapped types, every one of those derived shapes would need manual maintenance in lockstep with the source type.

    Q: How does `ReturnType<T>` work?

    Expected answer: a conditional type using `infer` — T extends (...args: any[]) => infer R ? R : never. It pattern-matches `T` against a generic function-type shape and captures whatever fills the return-position as a new type variable `R`. It's ordinary library code in lib.es5.d.ts, not a compiler primitive.

    Follow-up (Amazon/Google-style systems-thinking prompt): "Implement a type that extracts the resolved value of a function that returns a Promise." → compose two conditional types: Awaited<ReturnType<T>>, or write one directly with a nested `infer`.

    Don't recite definitions — narrate the COMPILER'S reasoning ("the checker builds a control-flow graph and narrows per-node," not "TypeScript is smart about ifs"). Interviewers at product companies are almost always probing whether you understand the type system as a real static-analysis tool with real internals, not a set of magic annotations.
